## 1. 背景と目的

### 1.1 背景【決定】
- 強度行動障害の症状は周囲の対応に困難をもたらし、虐待や不適切な支援に繋がることがある。
- 行動分析学に基づく支援は、問題行動の軽減だけでなく、望ましい行動の拡大とQOL向上を目的とする。
- 支援の有効性はエビデンス（記録・グラフ）を示しながら実施する必要がある。
- 家族・教員・施設職員などへのコンサルテーションと、チームでの一貫した支援が重要。
- これらを満たす、記録が簡単で共有しやすいツールが存在しなかった。

### 1.2 プロダクトの目的【決定】
1. 支援者が ABC記録・行動記録を簡単に残せる。
2. 行動の変化を折れ線グラフで見やすく表示できる。
3. 支援者間（家族・学校・施設・相談員）で簡単に共有できる。
4. AIが機能分析（機能的アセスメント）を補助し、代替行動・先行子操作の候補を提案する。
5. 誰もが使いやすい（ITに不慣れな家族・職員でも使える）。

### 1.3 プロダクトが目指さないこと【暫定】
- 診断や医療行為の代替（強度行動障害は診断名ではなく状態を表す行政用語）。
- 支援者の判断の代替。AIは仮説提示と候補提示に留め、決定は人が行う。
- 弱化（罰）・嫌悪刺激・身体拘束を「支援技法」として提案・推奨すること（禁止事項）。

## 2. 対象ユーザーと利用シーン

### 2.1 ユーザー種別【決定】
| 種別 | 具体例 | 主な利用 |
|---|---|---|
| 家族 | 保護者、きょうだい | 家庭での記録、グラフ閲覧、支援計画の確認、同意管理 |
| 施設職員 | 生活介護・入所施設・グループホーム・放デイの職員 | 勤務中の記録、申し送り、支援会議 |
| 教員 | 特別支援学校・学級の教員 | 学校での記録、家庭との共有 |
| 相談員・専門家 | 相談支援専門員、発達障害者支援センター、行動分析の専門家 | 機能分析、支援計画立案、チームへの助言 |
| 本人 | 対象者本人（可能な場合） | 【決定54】今は本人用のアカウントを作らない。成人して使える場合は管理者の引き継ぎで管理者になる（6.9） |

### 2.2 代表的な利用シーン【暫定】
- 出勤してアプリを開くと、現在時刻と「施設」が自動で表示される。開始ボタンは押さない。
- 自傷が起きた直後、職員が片手でスマホから10秒で「1回」を記録する。時刻と場所は自動で付く。
- 落ち着いた後に、その記録を開いてA（先行事象）・C（結果）を追記する。
- 週1回、相談員がグラフと ABC の集計を見て、AIの機能仮説を確認し、支援計画を更新する。
- 月1回の支援会議で、PDF出力したグラフと支援計画をもとに目標達成を判断する。
- 保護者が家庭の記録を入力し、学校・施設の記録と同じグラフで変化を見る。

### 2.3 導入単位と規模
- 【決定】まず無料・個人利用（家族・支援者が個人で登録）で検証する。課金やビジネスモデルは試用後に決める。
- 【暫定】法人アカウント管理（職員の一括登録・解除）は MVP に含めない。
- 【決定55】試用は5家族くらいまで。1対象者あたりのチーム人数は 3〜15名を仮置き【暫定】。

## 3. 設計原則（ガイダンス由来）【決定】

1. **非嫌悪的アプローチ**: 弱化・罰・身体拘束を支援技法として扱う機能を持たない。AIも提案しない。
2. **問題行動だけを数えない**: 望ましい行動・代替行動を必ず併記して記録・表示する。
3. **機能に基づく支援**: 4機能（注目・要求・回避/逃避・感覚）で仮説を立て、機能等価な代替行動を支援する。
4. **先行子操作の優先**: 環境調整（スケジュール、選択肢、視覚的支援、非随伴性強化、嫌悪刺激の除去）を結果操作より先に提示する。
5. **計画→実行→評価→修正**: 支援計画に達成基準を持ち、記録とグラフで定期的に見直す。
6. **チーム支援と孤立の防止**: 記録は個人の責任追及ではなくチームの共有財産。小さな成果を可視化し、支援者の行動を強化する。
7. **社会的妥当性**: 支援目標は複数の関係者の合意で決める。
8. **安全確保**: 危機的対応は「治療ではない」ことを明示し、身体拘束の3要件を記録で担保する。

## 5. プラットフォーム【決定】

**決定: Web/PWA をモバイルファーストで先行開発し、現場検証後に Phase 2 以降で Capacitor により iOS/Android ストア配布する（両方・PWA先行）。**

| 観点 | Web/PWA | ネイティブアプリ |
|---|---|---|
| 施設の共用PC・タブレット、家庭のスマホの両方で使う | ◎ | △（PC版が別途必要） |
| 法人・学校・家庭をまたいだ共有（URL招待） | ◎ | ○ |
| 配布・更新（ストア審査なし） | ◎ | △ |
| 自治体・法人の端末制限（アプリインストール不可） | ◎ | × |
| オフライン記録 | ○（Service Worker + IndexedDB） | ◎ |
| プッシュ通知 | ○（iOSはホーム画面追加が必要） | ◎ |
| 片手・即時記録の操作感 | ○ | ◎ |
| 開発コスト | 1コードベース | iOS/Android/Web で増加 |

- ストア配布は Capacitor で同一コードをラップする。ネイティブ固有機能（プッシュ通知、バックグラウンド同期）はラップ時に追加する。
- 【決定】ブラウザ版・ホーム画面の PWA・ストア配布版（Phase 2）は、同じアカウントで同じサーバーのデータを読み書きし、記録・グラフ・チーム共有はどれで開いても同じになる（決定13の同一コードによる）。ただし、(1) 電波がないときの記録は同期されるまでその端末にだけある（6.3.6）。(2) 同じ iPhone でも Safari とホーム画面の PWA は端末内の保存場所が別で、それぞれログインが要る。(3) 位置情報の許可と「位置情報 OFF」は端末ごとの設定（6.3.3a）。
- iOS Safari の PWA 制約（通知、ストレージ上限、バックグラウンド動作）を要件確認時に検証する。
- 【決定（制約）】iPhone の Safari・ホーム画面の PWA には振動の機能がない（Android の Chrome にはある）。また画面をロックすると PWA のタイマーと通知が止まる。このため Phase 1 では、振動を使う機能（6.3.1）はすべて**画面表示で代わりに知らせる方法を正**とし、振動は対応端末での上乗せとする。iPhone で振動が使えるのは Phase 2 のストア配布版（Capacitor）から。

## 6. 機能要件

### 6.1 対象者（本人）管理
- 【暫定】対象者ごとにプロフィール（表示名、生年月、所属、特性メモ、苦手な刺激リスト）を持つ。好きなもの・強化子は 6.14 の強化子リストで管理する。
- 【暫定】実名は必須にしない。イニシャルやニックネームで運用できる（要配慮個人情報の最小化）。
- 【暫定】1対象者 = 1「サポートチーム」。チームに家族・学校・施設の支援者を招待する。
- 【決定】対象者レコードの所有者は保護者（または本人）。法人・学校の支援者は参加者として招待される。退所・卒業後もデータは本人側に残る。
- 【暫定】法人をまたぐ共有範囲は、MVP では「チーム参加者は全記録を閲覧できる」とし、管理者が招待時の役割で制御する。記録ごとの公開範囲制御は Phase 2 以降で検討。
- 【暫定】（2026-11-05 の試作）対象者のプロフィール画面（チーム画面から開く）で、呼び名・生まれた年月・通っているところ・気をつけること（苦手な刺激など）を、管理者・副管理者・支援リーダーが変えられる。初回セットアップの対象者の欄にも、任意で同じ項目を置く。

### 6.2 行動定義
- 【決定】行動は3種類を扱う: **問題行動**、**望ましい行動**、**代替行動**。
- 【暫定】各行動に操作的定義（誰が見ても同じ判断ができる具体的な記述）、例、含まないものを記載する。
- 【決定】測定方法は行動（項目）ごとに1つ選ぶ。選択肢は NaviABA と同じ5種類:
  | 測定方法 | 記録UI | 向いている行動 |
  |---|---|---|
  | 頻度（事象記録法） | 起きるたびに +1 ボタン | 始まりと終わりがはっきりして数えやすい（叩く、特定の言葉） |
  | 持続時間記録法 | 「開始」「終了」のストップウォッチ | どのくらい続いたかを知りたい（かんしゃく、離席、集中） |
  | 潜時記録法 | 「指示を出した」「行動が始まった」のタイマー | きっかけから始まるまでの時間（呼名から振り向くまで） |
  | インターバル記録法 | 短い区間（既定10秒）ごとに有無を記録。画面の色と表示で区切りを知らせる（対応端末は振動も） | つきっきりで観察できる場面 |
  | 時間サンプリング法 | 決まった間隔（既定5分）で知らせ、その瞬間の有無を記録（Phase 1 は画面をつけたまま使う。5章の制約） | 他の作業をしながら記録する場面 |
- 【決定】行動を追加するとき、「測定方法ナビ」の質問に はい/いいえ で答えると測定方法が推奨される（NaviABA の MeasurementWizardView と同じフロー）。質問に答えず自分で選ぶこともできる。
  1. 指示やきっかけを出してから、行動が始まるまでの時間（待ち時間）を知りたいですか？ → はい: 潜時
  2. その行動がどのくらいの長さ（時間）続いているかを測りたいですか？ → はい: 持続時間
  3. その行動は始まりと終わりがはっきりしていて、1回、2回と数えやすいですか？ → はい: 頻度
  4. 観察している間、対象者からずっと目を離さずに記録し続けられますか？ → はい: インターバル / いいえ: 時間サンプリング
- 【暫定】強度レベルは測定方法とは別の「付加項目」とし、どの測定方法にも任意で付けられる。
- 【決定】強度は数字だけで示さず、ABC記録の B の欄に「強度」というラベルと、行動ごとに決めた各段階の基準（観察できる具体的な指標）を並べて表示し、観察者間で同じ判断ができるようにする。
- 【暫定】基準は行動の追加・編集時に段階ごとに記述する（例: 頭たたき 1 = 1〜2回で止まる・赤みなし / 2 = 3回以上続く・声かけで止まる・赤みあり / 3 = 声かけで止まらない・腫れや出血・安全確保が必要）。基準が未記入の段階は ABC記録で「基準未設定」と表示し、記入を促す。
- 【暫定】追加ウィザードは3ステップ（1 種類と名前・操作的定義 → 2 測定方法ナビ → 3 確認）。測定方法は後から変更でき、変更時はグラフに注記を自動挿入する（変更前後のデータは別系列として扱う）。
- 【暫定】（2026-11-07 の試作）測定方法ナビの各質問の下に、その質問に「はい」になりやすい行動の例を1行出す（例: 頻度は「たたく、手を挙げる、決まった言葉を言う」）。推奨が出たあとに「もう一度答える」で質問1からやり直せる。
- 【暫定】（2026-11-05 の試作）グラフの注記ができるまでは、行動の編集画面では測り方を変えられないようにし、「新しい行動として追加」を案内する。名前・定義・例・含まないもの・区間の長さ・強度の基準・代替行動のリンクは編集でき、前の内容は監査ログに残る（BehaviorVersion の代わり）。（2026-11-07: 「定義の変更」の線はできたが、変更の前と後を別の系列として扱う部分がまだのため、測り方の変更はまだ開けていない）
- 【暫定】強度は 3段階を既定（1: 軽微・介入不要 / 2: 中・声かけや誘導で収まる / 3: 重・安全確保やけが・物損あり）。5段階に変更可。段階ごとの定義を行動ごとに書く。
- 【暫定】代替行動は「どの問題行動の代替か」「どの機能に対応するか」をリンクで持つ。
- 【暫定】行動定義の変更は履歴を残す（定義が変わると前後のデータ比較ができなくなるため、変更時はグラフに注記を自動挿入）。
- 【暫定】（2026-11-07 の試作）記録がある行動の定義・例・含まないもの・区間の長さ・サンプリングの間隔・強度の基準を変えると、「行動の定義の変更」を1件残す（変えた人・日時・変えた項目の名前。前と後の中身は監査ログに残る）。名前だけを変えたときと、まだ記録がない行動を変えたときは残さない。グラフ・支援会議メモ・PDF レポートには、その日に「定義の変更」の縦の点線を引く（同じ日に何回変えても1本）。計画の縦線と同じく線の前後をつながないが、「ベースライン」の名前は計画の線だけで決める。変化のまとめ（6.4.1）の期間に定義の変更が入るときは「間に定義の変更あり」と書き添える。この記録はあとから変えられず、消せない（サーバーはマイグレーション 0017）。
- 【暫定】インターバル記録は部分インターバル（区間内に1回でも起きたら「あり」）を既定とし、区間長は 5〜60秒で設定可。時間サンプリングは 1〜30分で設定可。
- 【決定】行動（項目）は削除できる。
- 【暫定】削除の既定は「非表示」（ホーム・グラフ・集計から消えるが記録は残り、いつでも元に戻せる）。「記録ごと削除」は**管理者のみ**が実行でき（支援リーダー・支援者は非表示まで）、確認ダイアログで記録件数を示す。削除しても監査ログには「誰が・いつ・どの行動の記録を何件削除したか」が残り、この監査ログは誰も消せない。施設・学校の職員は記録を消せない（記録は虐待防止の証拠でもあるため）。


### 6.3 記録

#### 6.3.1 クイック記録（最重要）
- 【暫定】ホーム画面に対象者ごとの行動ボタンを並べる。ボタンの記録UIは行動の測定方法で変わる（頻度: 1タップで +1 / 持続時間: 開始・終了 / 潜時: 指示・開始 / インターバル・時間サンプリング: 観察セッション中に区間ごとの あり・なし）。
- 【決定】各行動カードの右上に、「−1」と書いた小さなバッジ（見た目 24px・タップ領域 32px）を常時置き、押し間違いをその場で取り消せる（時間制限なし）。最後の記録を1件取り消し、取り消しも監査ログに残す。持続時間などタイマー型の行動では「取消」と書いた同じ大きさのバッジで直前の計測を取り消す。バッジの色と形は赤い丸に限らず、画面のデザインに合わせる（決定117）。記号だけのアイコンは使わず、機能が文字で分かるようにする。
- 【暫定】（2026-11-07）−1 は日付で区切らず、その行動のいちばん新しい記録を取り消す（支援者は自分の記録だけ、管理者・副管理者・支援リーダーはほかの人の記録も。6.3.5）。ほかの人の記録か今日より前の記録のときは、記録した人と日時を出して確かめてから取り消す。取り消したあと5秒ほど「元に戻す」を出す。
- 【決定】記録時に触覚フィードバックを返し、問題行動は強め、代替行動・望ましい行動は「成功」の振動にして区別する（対応端末のみ。音は鳴らさない）。
- 【暫定】振動が使えない端末（Phase 1 の iPhone など、5章）では、押したカードが一瞬色づき（問題行動は灰、代替行動・望ましい行動は緑）、画面下に「+1 を記録しました」を表示して、記録できたことを目で確かめられるようにする。この表示は振動できる端末でも常に出す。
- 【決定】ホームの並び順は、代替行動を対応する問題行動の右隣に置く。代替元のない行動はその後に並べる。
- 【決定137】ホームの行動カードは、スマホのアイコンのように並べかえられる。カードを長押しすると並べかえの状態に入り、指で引っぱって動かし、「完了」で終える。並べかえの間は、カードを押しても +1 にならない。代替行動は対応する問題行動とひと組のまま動く（上の決まりを守る）。並びはこの端末だけのもの（端末の設定に保存し、チームには共有しない）。「はじめの並び」で元の並びに戻せる（発注者回答 2026-11-08）。【暫定】長押しは 0.5 秒。並べかえの間はカードが小さく揺れる（動きを減らす設定の端末では揺れずに点線の枠）。ひと組のカードが左右の列に分かれそうなときは、左に空きを1つ入れて同じ行にそろえる。あとで足した行動は、並びのうしろに付く。
- 【暫定】（2026-11-07 の試作）代替行動のカードの種類の印には、置きかえる問題行動の名前も出す（例: 「代替行動（頭たたき）」）。
- 【暫定】持続時間はボタンでタイマー開始・停止。手入力も可。
- 【決定】インターバル記録・時間サンプリングの記録UI（NaviABA 準拠）: 区間ごとの結果を ○（起きた）× （起きなかった）で横一列に並べて表示し、区間の残り時間をバーで示す。残り 20% を切るとバーが赤くなり、区間が終わると画面全体の枠が光り「記録してください」と表示する（対応端末は振動も）。記録中は画面が消えないようにする（画面の点灯維持）。時間サンプリングは固定間隔のみ（ランダム間隔は採用しない）。
- 【決定】○× の付け方（決定118）: 「○ 起きた」が押されなかった区間は、自動で「× 起きなかった」にする。画面のボタンは「○ 起きた」だけにする（× のボタンは置かない）。
  - インターバル（部分インターバル）: 区間の途中で「○ 起きた」を押せて、押した区間は区間が終わったときに ○、押さなかった区間は ×。答えを待つことはないので、区間の終わりは振動だけで知らせ、枠は光らせない（決定28 の「記録してください」は、答えを待つ区間があるときだけ）。
  - 時間サンプリング: 区切りで枠が光り、次の区切りまでに「○ 起きた」を押せば ○、押さなければ ×。
  - 「観察を終える」を押したとき、答えを待っていた区間は ×。インターバルの途中の区間は「○ 起きた」を押していれば ○、押していなければ数えない。
  - 画面を消した・ほかのアプリに切り替えた間に終わった区間は「未観察」のまま（下の Phase 1 の制約）。割合（6.4.1）は未観察を除いて計算する。
- 【暫定】（2026-11-07 の試作）インターバル・時間サンプリングの観察中は「直前の区間を取り消して答え直す」を出す。取り消せるのは、いちばん新しい区間だけ。次の区間が終わる前に「○ 起きた」を押さなければ × になる（決定118）。「未観察」になった区間は取り消せない。今の区間に先に付けた ○ は、そのまま残る。
- 【暫定】Phase 1（PWA）の時間サンプリングは、画面をつけたままの観察セッションとして使う。画面をロックしたり他のアプリに切り替えたりすると知らせが止まるため、戻ったときに「抜けた区間」を「未観察」と表示し、○× を推測で埋めない。画面を消しても知らせが届くのは Phase 2 のストア配布版から。
- 【暫定】強度はタップ後にシートで選択（スキップ可、未入力は「未評価」）。
- 【暫定】（2026-11-07 の試作）強度のシートには、記録した時刻と場所を出す（例: 「記録しました ・ 14:05 ・ ひまわり園」）。「あとで（未評価）」で閉じられ、「詳細を追加（ABC）」でそのままその記録の ABC記録を開く。
- 【決定】強度のシートでは、「あとで（未評価）」をいちばん上（強度の選択肢より上）に置く（決定110）。
- 【暫定】記録に「詳細を追加」すると ABC記録に昇格する。

#### 6.3.2 ABC記録
- 【決定】A（先行事象）/ B（行動）/ C（結果）を記録する。
- 【決定】A（先行事象）・C（結果）・状況要因の選択肢は、その場で追加・削除できる。
- 【暫定】各セクションの「編集」で編集モードに入り、選択肢の × で削除、入力欄で追加する。削除した選択肢は非表示になるだけで、過去の記録に付いた値は残る（集計にも残る）。選択肢の変更はチーム内で共有される（対象者ごとのテンプレート）。
- 【暫定】各項目は「選択肢 + 自由記述」。初期テンプレートを用意する。
  - A の例: 要求を断られた、活動の切り替え、待ち時間、騒音、人が近づいた、課題提示、注目がなくなった、体調不良
  - C の例: 注目した（声かけ・制止）、要求が通った、活動を中止した、課題を取り除いた、無視した、場所を移した、物を取り上げた
- 【暫定】「状況要因・確立操作」欄（睡眠不足、空腹、服薬変更、体調、環境の変化）を A とは別に持つ。
- 【暫定】場面（場所・活動・関わった支援者）を記録する。問題行動が起きやすい/起きにくい条件の特定に使う。
- 【暫定】記録者が「この時の機能はこれだと思う」を任意で付けられる（AIの仮説と比較する材料）。
- 【暫定】ABC記録への写真添付は行わない（写真は 6.14 の強化子リストのみ）。
- 【決定48】ABC記録などの自由記述は、文字入力と音声入力の両方で書ける。音声入力は端末の音声入力機能で話した言葉を文字にするもので、録音そのものは保存しない（7.4.1「集めない」）。

#### 6.3.3 観察時間と場所（自動）
- 【決定】ホーム画面に「観察開始」「観察終了」ボタンは置かない。毎日押すことは支援者の負担になるため。
- 【決定】ホーム上部に現在時刻と現在の場所を表示し、記録にはその時刻と場所が自動で付く。
- 【暫定】（2026-11-07 の試作）時刻の前に今日の日付も出す。「今日の記録」には、メンバーが2人以上いるときに記録した人の名前も出す（人ごとの集計やランキングは作らない。14.2 #16）。
- 【暫定】（2026-11-07 の試作）ホーム上部の場所の横に、位置で自動判定した場所か、手で選んだ場所かを出す（「（自動判定）」「（手で選んだ）」）。この区別は端末の中だけに覚え、サーバーには送らない。
- 【暫定】（2026-11-07 の試作）記録を保存する瞬間の場所の判定: 記録はすぐ保存し、そのあとで位置を1回取り直す。別の登録場所に入っていたら、その記録の場所を直し、知らせの文に「（場所: 〇〇）」を足す。手で選んだ場所は上書きしない。インターバル・時間サンプリングの観察にも、始めたときの場所の名前を残す（マイグレーション 0019）。
- 【暫定】場所は、チームで登録した「場所」（例: 自宅、学校、施設）のうち、端末の位置情報に最も近いものを端末内で判定して表示する。登録は住所検索または「いまここを登録」で行い、半径（既定 100m）を持つ。
- 【暫定】場所の登録画面（ホーム上部の場所ボタンから開く）:
  - 登録した場所の一覧（名前・種類・半径・登録者）。いまいる場所に「いまここ」と印を付ける。
  - 追加は「いまここを登録」を主にし、「住所で探す」も用意する。地図上の円でピンと半径を確かめ、ピンは指で動かせる。
  - 入力は 名前・種類（自宅 / 学校 / 施設 / その他）・半径（50m / 100m / 200m）。
  - 【決定43】場所は「施設」「自宅」「学校」のように建物・敷地の単位で1つずつ登録し、1つの建物を部屋（作業室・食堂など）に分けない。部屋や場面の違いは ABC記録の「活動」（個別課題、食事など）で記録する。登録場所の外（移動中・外出先）では「登録場所の外」と表示し、必要なら手で選ぶ。
  - 自宅は住所を一覧に表示しない。
  - 同じ画面に「わたしのいつもの時間」（記録者ごとの勤務・在宅時間のテンプレート。観察時間の推定に使う）と、「この端末で位置情報を使う」のスイッチを置く。
  - 【決定85】「住所で探す」と地図には国土地理院の住所検索と地理院タイルを使う（無料・登録なし。地図に出典「国土地理院」を表示する）。
  - 【暫定】（2026-11-05 の試作）追加は「いまここを登録」（位置を1回だけ取って中心にする）と「位置なしで登録（手で選ぶ）」で始めた。「わたしのいつもの時間」は 2026-11-06 に足した（下の観察時間の試作を参照）。位置情報のスイッチはこの端末だけの設定で、既定はオフ。
  - 【暫定】（2026-11-07 の試作、決定88）「住所で探す」を足した。住所を入れると国土地理院の住所検索で候補（多くて5件）を出し、選ぶと地理院タイルの地図にピンと半径の円が出る。ピンは指で動かせ、地図をタップしても動く（住所検索の中心は町や番地の目安のため）。登録済みの場所の編集でも地図を出し、「住所で探しなおす」で中心を変えられる。
    - 住所の文字は中心を探すのに使うだけで保存しない（データモデルの「住所［任意］」は持たない。自宅の住所が一覧に出ることもない）。
    - 地図は「住所で探した場所」と「登録済みの場所」にだけ出し、「いまここを登録」と「中心をいまここにする」では出さない。地図の画像を読みこむと、その位置が国土地理院に伝わるため（6.3.3a、支援者の現在地を送らない）。
    - 住所で探した場所を登録しても、いまの場所には切りかえない（「いまここ」で登録したときだけ切りかえる）。
  - 場所の追加・編集は支援者以上。削除は非表示扱いで、過去の記録に付いた場所名は残る。
- 【決定】アプリを起動したとき（および他のアプリから戻って前面に復帰したとき）に位置情報を自動で取得し、登録場所に一致すれば場所を自動で切り替える。支援者がボタンを押す必要はない。
- 【暫定】自動取得の動作:
  - 取得は1回だけ（連続取得しない）。タイムアウト 5秒、精度は粗くてよい（半径100m の判定に十分）。
  - 取得中は前回の場所を表示し、判定が終わったら切り替えて「場所を 施設 に切り替えました ・ 元に戻す」を3秒表示する。
  - 登録場所のいずれにも入っていないときは「登録場所の外」と表示し、場所は手動選択に任せる。
  - 記録を保存する瞬間にも同じ判定を1回行い、記録に付く場所を最新にする。
  - 位置情報の許可は初回起動時にアプリ内の説明画面を出してから OS の許可ダイアログを表示する。許可は「アプリ使用中のみ」で十分で、「常に許可」は求めない。
- 【暫定】判定結果はタップで手動変更できる。位置情報を許可していない、または屋内で判定できない場合は「場所: 未設定（タップして選ぶ）」と表示し、前回選んだ場所を既定にする。
- 【暫定】PWA では Web の Geolocation API を使う。ホーム画面に追加した PWA では許可が記憶されるため、2回目以降は自動で取得できる。ブラウザで開いた場合は端末設定により毎回確認が出ることがある。Phase 2 のストア配布版（Capacitor）では OS 標準の位置情報許可を使い、より安定する。
- 【暫定】位置情報を持たない共用 PC では IP アドレスやWi-Fi による粗い判定になるため、自動切替は行わず前回の場所を既定にする。
- 【暫定】観察時間は手動のセッションではなく、記録者ごと・日ごとの「在席時間」から自動推定する。推定の優先順位は、(1) 記録者が設定した勤務時間・在宅時間のテンプレート（例: 平日 9:00〜16:00 は施設）、(2) その日、アプリを開いた・記録した時刻のうち、同じ登録場所で判定された最初から最後まで、(3) その日の最初の記録から最後の記録まで。位置はアプリを開いたときと記録したときにしか取らない（6.3.3a）ため、登録場所への出入りの時刻そのものは分からない。(2) は「その場所にいたことが確認できた時間」の目安として使う。初回セットアップで勤務時間・在宅時間のテンプレートを登録するよう案内する。推定方法はグラフに注記し、必要なら支援者が後から編集できる。
- 【暫定】観察時間が推定できない日は「1時間あたりの率」を出さず「生起数」のみ表示する。
- 【暫定】（2026-11-06 の試作）観察時間の推定と「わたしのいつもの時間」:
  - 「わたしのいつもの時間」は、1人につき対象者ごとに1つ（曜日・はじめ・おわり・場所の名前［なくてもよい］）。場所の画面でチームの全員の分が見られ、作る・直す・消すのは本人だけ（支援者以上）。夜をまたぐ時間はまだ登録できない。サーバーでも本人以外は書けない（RLS）。
  - その日に記録（クイック記録・インターバル記録）を付けた人ごとに、いつもの時間にその曜日が入っていれば (1) その時間帯、なければ (3) その人のその日の最初の記録から最後の記録まで、を観察時間とする。何人かいるときは時間帯を重ねて合わせる（足し算しない）。合わせて30分に満たない日は推定できないとして率を出さない。
  - (2) アプリを開いた時刻はまだ残していないので使わない。観察時間を後から手で直す機能もまだない。
  - 初回セットアップの4つめ（場所の画面）で、場所と一緒に「わたしのいつもの時間」を案内する（2026-11-06）。招待で参加した人は、承認されたときにこの画面を開き、場所といつもの時間だけを案内する（支援者以上のとき。閲覧者は登録できないので案内しない）。承認を待つ画面を閉じたあとに承認された場合は案内しない。
  - 自動 0 の条件は変えない（その対象者に何か記録がある日）。
  - 【決定】行動を作った日より前の日には、自動 0 を付けない（決定111。グラフ・時間帯の図・「さかのぼって入力」の自動 0 の一覧）。
  - 【暫定】（2026-11-07 の試作）「さかのぼって入力」で、作った日より前の記録を足したときは、その記録の日から自動 0 を付ける。
- 【決定】「本日なし」ボタンは置かない。記録がない行動は自動的に 0 として記録される。
- 【暫定】自動 0 の条件: 記録者の在席が推定された日（6.3.3 の位置判定・テンプレート・他の行動の記録のいずれかがある日）に、その行動の記録が 1件もない場合、日の終わり（23:59）に 0 を自動記録する。在席が推定できない日（休日・欠席など）は「未記録」のままにし、グラフでは線を切る。
- 【暫定】自動 0 を付けるのは、「0」に意味がある測定方法だけにする:
  | 測定方法 | 記録がない日 |
  |---|---|
  | 頻度 | 自動で 0回 |
  | 持続時間 | 自動で 0分 |
  | 潜時 | 付けない（「待ち時間 0秒」は「すぐ始まった」の意味になり、起きなかったことと区別できないため）。未記録のまま |
  | インターバル・時間サンプリング | 付けない。観察セッションを行った区間だけが記録になり、行わなかった日は未記録のまま |
- 【暫定】オフラインで記録した分が日付をまたいで後から同期された場合は、同期された記録を正とし、その日の自動 0 を取り消す（履歴は残す）。
- 【暫定】自動 0 は「自動」と印を付けて保存し、「さかのぼって入力」から「観察していなかった（未記録に戻す）」に変更できる。
- 【暫定】（2026-11-05 の試作）端末内だけで動く間は、自動 0 は保存せずグラフを描くたびに計算し、「観察していなかった」にした日だけを NoEventDay として保存する（0 に戻すと論理削除。どちらも監査ログに残る）。「さかのぼって入力」には直近14日の自動 0 を並べる。インターバル・時間サンプリングは区間ごとの観察なので、あとから足せない。

#### 6.3.3a 位置情報のプライバシー【決定（遵守すること）／方式は暫定】
- 位置情報の利用は支援者本人の端末・本人の同意（OS の許可と、アプリ内の説明付き同意）に限る。対象者の端末を追跡する機能は持たない。
- **支援者の現在地**の緯度経度はサーバーに送らず保存もしない。端末内で登録場所と照合し、記録に保存するのは「場所の名前」と時刻だけ。
- 【決定42】照合に使う**登録場所の中心と半径**は、住所と同じ扱いでチーム内だけで共有する（他の支援者の端末でも判定できるようにするため）。エクスポートには含めない。
- 「住所で探す」では、入力した住所の文字だけを地図サービス（国土地理院、決定85）に送り、現在地は送らない。
- 位置の取得はアプリを開いたとき・記録したときに限り、バックグラウンドでの常時追跡は行わない。
- 位置情報を使わなくても全機能が動く（場所は手動選択、観察時間はテンプレートか記録範囲から推定）。
- 設定画面でいつでも OFF にでき、OFF にしても過去の記録に付いた場所名は残る（記録の文脈として必要なため）。
- 登録場所の住所はチーム内のみで共有し、エクスポートには場所名だけを含める。

#### 6.3.4 睡眠ログ（任意）
- 【決定】何時に寝て何時に起きたかを簡単に記録できる。入力は任意で、未入力でも催促の通知は出さず、他の機能（自動0、グラフ、状況要因）に影響しない。
- 【決定】睡眠の入力・変更ができるのは、管理者・副管理者と、チームで「家族」の印が付いたメンバー（父、きょうだいなど。役割が支援者でもよい）。それ以外の職員・教員は閲覧のみ。
- 【決定96】「家族」の印は、管理者が招待時またはメンバー一覧で付け外しする。役割（6.9）とは別の印で、睡眠の入力以外の権限は変わらない。
  - 【決定96】「家族」の印を付け外しできるのは管理者だけ。招待のときに管理者が「家族」の印を付けて招待でき、参加した人の印は招待コードの印だけで決まる（参加する人が所属を「家族」と選んでも印は付かない）。支援リーダー・副管理者が印や「睡眠の入力を許可」を変えようとしても、サーバーが前の値のまま残す（マイグレーション 0018）。すでに付いている印はそのままで、管理者がメンバー一覧で見直せる。
- 【暫定】入所施設などで夜間を職員が把握している場合は、管理者がその職員に「睡眠の入力を許可」を個別に付ける。支援リーダーの役割を渡す必要はない（招待や権限変更の権限まで渡さないため）。
- 【暫定】入口はホームの1行カード（「睡眠（昨夜） 21:30 → 6:45 ・ 9時間15分 ・ 母 が入力」、右端に「入力・変更」）。未入力時は「睡眠を記録（任意）」。入力できないメンバーには同じカードが閲覧専用で表示され、睡眠ログ画面も一覧だけが見える。
- 【暫定】睡眠ログ画面の入力方法:
  - 昨夜の「寝た」「起きた」の時刻は、時と分のホイール（上下にくるくる回す、分は5分刻み）で入力して保存する。「いま寝た / いま起きた」のような現在時刻を押す1タップボタンは置かない。ボタンのタップで時刻を進める方式も使わない。「いつもの時刻」（過去2週間の中央値）でまとめてセットできる。
  - 「前の日」で過去の夜をさかのぼって入力できる。
  - 中途覚醒の回数（−/＋）とメモは任意。
  - 【決定115】中途覚醒は、対象者ごとに「使う・使わない」を選べる。「使わない」にすると、睡眠の入力画面とホームの睡眠のカードに中途覚醒が出ない。
  - 【暫定】初期は「使う」。切りかえはチームの設定で、睡眠不足の判定と同じく管理者・副管理者が行う。「使わない」にしても、これまでの回数は消さない（CSV にはそのまま出る）。サーバーの列はマイグレーション 0025。
  - 記録日は起床日に紐づける。寝た時刻が前日夜でも1件として扱う。
- 【暫定】1週間（7日分）の一覧を棒で表示し、「睡眠が短かった夜」はオレンジで示す。
- 【暫定】（2026-11-07 の試作）1週間の一覧には、睡眠の長さの横に寝た時刻と起きた時刻（例: 21:30→6:45）も出す。
- 【暫定】（2026-11-07 の試作）ホームの睡眠のカードに中途覚醒の回数も出す（例: 「中途覚醒 1回」）。睡眠ログ画面の「この1週間」の横に「グラフで見る」を置き、睡眠時間のパネルを出した状態でグラフを開く。
- 【暫定】「睡眠が短かった」の判定は、既定では **いつもの睡眠時間（過去2週間の中央値）より 2時間以上短い夜** とする。年齢によって必要な睡眠時間が違うため、決まった時間で区切らない。記録が 5夜分たまるまでは判定しない。管理者は設定で「○時間未満」に変えられる。
- 【暫定】睡眠が短かった夜の**起床した日**（その夜が明けた日）の ABC記録に、状況要因「睡眠不足」を自動で付ける（記録者が外せる）。睡眠は起床日の記録として保存するので、同じ日付どうしで結びつく。睡眠が未入力の日は何も付けない。
- 【暫定】グラフ画面に「睡眠時間」パネルを追加できる（表示する行動の選択と同じ場所で ON/OFF）。Phase 2。
- 【暫定】同じ夜に2件あれば後から入力した方を採用し履歴を残す。

#### 6.3.5 事後入力・編集・監査
- 【暫定】日時をさかのぼって入力できる。
- 【暫定】記録の編集・削除は履歴を残す（誰が・いつ・何を変えたか）。記録は支援の証拠であり、虐待防止の観点でも改ざん防止が必要。
- 【暫定】（2026-11-06）サーバーに送られた変更は、データベースが自分で監査ログに残す（マイグレーション 0010。記録・行動・対象者・メンバー・設定・支援計画・拘束記録・会議メモ・コメント・場所・睡眠・好きなもの など、チームのデータの表すべて）。作る・変える・取り消す・元に戻すのたびに、変える前と後の内容を残す（写真の中身は入れない）。手を加えた端末でも、記録を残さずに変えることはできない。端末が作る監査ログ（書き出しなど）もこれまでどおり送り、データベースが残したものと区別する。同じ変更が両方に残ることがあるが、監査ログを見る画面を作るときにまとめる。閲覧の記録は、チームを開いた日だけを残す（決定102、マイグレーション 0022）。運営者が SQL Editor で直したものの記録はまだない。
- 【暫定】削除は論理削除。
- 【暫定】記録1件の「取り消し」（−1・取消バッジ、記録詳細からの削除）は論理削除で、履歴に残り元に戻せる。取り消し・編集ができるのは、その記録をした本人と、管理者・副管理者・支援リーダー。支援者は他の人の記録を変えられない。
- 【暫定】（2026-11-07）記録の詳細（ABC の画面）に「この記録を取り消す」を置く。取り消した記録を開くと「取り消した記録」と出て、「元に戻す」で戻せる（付いていた ABC もそのまま戻る）。取り消した記録は「さかのぼって入力」の画面に直近14日分を並べ、そこから開ける。期限はなく、14日より前の記録も詳細からなら戻せる。
- 【暫定】（2026-11-07 の試作）記録の詳細（ABC の画面）で、日時・回数・持続時間・待ち時間（潜時）をあとから直せる。未来の日時にはできず、回数は 1〜999。直した項目は監査ログに残る。
- 【暫定】6.2 の「施設・学校の職員は記録を消せない」は、記録を履歴ごと完全に消すこと（行動の記録ごと削除）を指す。完全に消せるのは管理者だけ。

#### 6.3.6 オフライン
- 【暫定】電波がない場所（施設内、移動中）でも記録でき、復帰後に同期する。
- 【暫定】記録は追記型のため競合はほぼ発生しない。同一記録の編集競合は「後勝ち + 履歴保持」。

### 6.4 グラフ・可視化

#### 6.4.1 折れ線グラフ【決定（機能）／詳細は暫定】
- X軸: 日 / 週 / 月（切替）。
- 【決定】頻度・持続時間・強度は縦軸の切替ではなく、それぞれ別のパネル（グラフ）として縦に並べて表示する。頻度パネルは生起数または1時間あたりの率、持続時間パネルは1日の合計（分）、強度パネルは1日の平均（段階）。
- 【暫定】（2026-11-06 の試作）頻度の行動があるときだけ、グラフ画面に「回数 / 1時間あたり」の切りかえを置く。既定は回数。1時間あたり = その日の回数 ÷ 観察時間（6.3.3 の推定）で、小数1けた。推定のしかたを切りかえの下に書く。達成基準は1日の回数で決めているので、1時間あたりのときは達成基準の横線を出さない。PDF レポート・支援会議メモ・「できたこと」は回数のまま。
- 【暫定】残りの測定方法も、それぞれのパネルに表示する: 潜時パネルは1日の平均（秒）、インターバル・時間サンプリングパネルは「観察した区間のうち起きた区間の割合（%）」。インターバルと時間サンプリングはどちらも割合なので同じパネルにまとめる。そのパネルの行動がない場合はパネル自体を出さない。
- 【暫定】各パネルには、その測定方法で記録している行動だけを表示する（頻度で記録する行動は頻度パネル、持続時間で記録する行動は持続時間パネル、強度を付加した行動は強度パネル）。
- 問題行動と代替行動・望ましい行動を同じパネルに重ねて表示できる（同じ測定方法の場合）。
- 【暫定】問題行動とその代替行動の測定方法が違う場合（例: 大声は持続時間、代替行動は頻度）は重ねず、2つのパネルを上下に続けて並べ、日付の目盛りとフェーズ線の位置をそろえる。2つのパネルは同じ枠で囲み、見出しに「大声 と 静かに伝えるカード」のように両方の名前を書く。
- 【決定】条件を変更した点（フェーズ変更線）の前後で、点と点の間の線をつながない。フェーズごとに別の線として描く。
- 【決定】どのグラフがどの行動かを一目で分かるようにする:
  - 各パネルの見出しは行動名を大きく表示し、線の色見本（実線・点線）と種類チップ（問題行動 / 代替行動 / 望ましい行動）を行動名の横に付ける。測定方法（頻度・持続時間・強度）と単位は見出しの下に小さく書く。
  - 折れ線の右端に、その線の行動名を線と同じ色で書く。凡例をグラフの下に置かない。
  - 縦軸の単位（回/時、分、段階）をグラフの左上に書く。
- 【決定65】X軸・Y軸の値をはっきり書く:
  - 縦軸（Y軸）: 目盛りの数値を等間隔に書き、薄い横の目盛り線を引く。左上に軸の名前と単位を書く（例: 「1時間あたりの回数（回/時）」「1日の合計（分）」「1日の平均強度（段階）」「できた区間の割合（%）」）。強度は 1〜3（5段階なら 1〜5）、割合は 0〜100% で固定し、回数・分は記録の最大値に合わせて切りのよい数まで取る。
  - 横軸（X軸）: 1日ごとに目盛りを付け、日付（例: 10/28）と曜日を書く。日付が重なるときは1日おきに書く（目盛りは毎日）。週・月の表示では「10/8〜」のように期間の始まりを書く。右下に軸の名前（「日付（1日ごと）」「週（1週間ごと）」）を書く。
  - 線の右端に、行動名と最後の値（例: 1.9回/時）を書く。
  - 【決定95】グラフの見出しの行動名の前に、線の見本（色・実線か点線か・印の形）を付け、どの線がどの行動か分かるようにする。
  - PDF レポートと支援会議メモに入れるグラフも同じ書き方にする。
- 【決定66】グラフは横にスクロール（指で左右にスワイプ）して、過去の記録までさかのぼって見られる。細かい動きは実装のときに決める。
  - 【決定73】縦軸（目盛りの数値と軸の名前）はスクロールしても左に残す。縦に並んだパネルは一緒に動き、日付がずれない。
  - 【決定73】初めは直近の期間（日表示なら14日）を表示し、右端が今日。左へスクロールすると古い記録を読み込む。「今日に戻る」ボタンを置く。
  - 【決定73】縦軸の目盛りは表示中の期間で変えず、記録全体の最大値に合わせる（スクロールのたびに目盛りが変わると比べにくいため）。
  - 【暫定】条件変更の縦の点線とその名前は、どこまでスクロールしても表示する。
  - 【暫定】（2026-11-05 の試作）週・月の値は、その期間のうち値のある日（記録した日・自動 0 の日）の平均にする。値のない日は平均に入れない。
  - 【暫定】（2026-11-05 の試作）縦の線の名前は、最初に計画が実施中になった日を「支援開始」、そのあとを「計画の変更」とし、最初の線より左の左上に「ベースライン」と書く。達成基準の横線の名前（例: 目標 3回以下）が同じ高さで重なるときは、上下にずらして書く。
  - 【暫定】（2026-11-07 の試作）同じ日に計画の変更と定義の変更があるときは、縦線を1本にして名前を「計画の変更・定義の変更」とつなぐ。縦線の名前や「ベースライン」が横に重なるときは、1段上に書く（そのぶんグラフを下げる）。
  - 複数の行動を重ねるのは「問題行動とその代替行動」の組み合わせだけにし、見出しに「頭たたき と 休憩カードを渡す」のように両方の名前を書く。
  - 【決定】グラフ画面に表示の切りかえを置き、一緒にできるもの（問題行動どうしの頻度、問題行動と代替行動など）は1つのグラフにまとめて表示できるようにする（決定112）。
  - 【決定】まとめて表示するときの組み方（決定113）: (1) 代替行動のある問題行動は、その代替行動とだけ組にして1つのグラフにする（例: 頭たたき と 休憩カードを渡す）。(2) 代替行動のない問題行動どうしは、同じにできるもの（測定方法と単位が同じもの）を1つのグラフにする。(3) 望ましい行動どうしも同じ。
  - 【決定】組の優先順位の一番は「問題行動と代替行動」の組にする（決定114）。支援計画で「標的とする問題行動」と「代替行動」に選んだ組は、行動の設定（どの問題行動の代わりか）より優先して、1つのグラフにする（「行動ごと」「まとめて」、支援会議メモ、PDF レポートのどれでも）。
  - 【暫定】（2026-11-07 の試作）切りかえの名前は「まとめ方」で、「行動ごと」（既定。上の書き方）と「まとめて」。表示中の行動が2つ以上のときだけ出す。(1) の組は、代替行動のない問題行動とは重ねない。強度は、同じ組の中で段階の数が同じものを重ねる。重ねた線は色だけでなく点の形（丸・三角・ひし形・四角）でも見分けられるようにする。支援会議メモ・PDF レポートは「行動ごと」のまま。
- フェーズ変更線（ベースライン → 支援開始 → 支援修正）を縦の点線で表示する。【Phase 2】
- 達成基準線（支援計画の目標値）を横線で表示する。【Phase 2】
- 記録がない日はゼロとして描かず、線を切る（欠損扱い）。
- 【暫定】（2026-11-07 の試作）グラフの上に、いま出している期間（例: 10/24 〜 11/7（15日））を書く。最初の記録と最後の記録の間で、どの線にも値がない日には、グラフの下に「未記録」と書く（続く日はまとめて1つ）。
- 【暫定】（2026-11-07 の試作）各パネルに「変化のまとめ」を1行出す。前と後がどちらも3日以上ある計画の変更のうち、いちばん新しいものの前と後の1日あたりの平均を並べる（例: 「支援開始（10/20）の前 → 後の平均」）。計画の変更がなく記録が14日以上あるときは、最初の7日と最近の7日の平均を並べる。どちらでもないときは出さない。日・週・月の切りかえにかかわらず1日ごとの値で計算する。良くなった・悪くなったの判定の言葉は付けず、数字だけを出す。
- 色覚多様性に配慮した配色。印刷でも区別できる線種。

#### 6.4.2 スキャッタープロット【暫定 / Phase 2】
- X軸: 日付、Y軸: 時刻（30分刻み）、セル: 生起の有無・強度。時間帯パターン（午後に集中、食事前に多い等）を発見する。
- 【暫定】1週間ずつ表示し、行動を1つ選ぶ。強度は色と数字の両方で示し（色だけに頼らない）、観察しなかった日は灰色にする。グラフ画面から開く。
- 【暫定】（2026-11-05 の試作）グラフ画面の上に「折れ線・時間帯・ABC分析」のタブを置いて切りかえる。PDF レポートでは、期間が長くても1枚に収まるよう、行動ごとに「1時間ごとの合計」を色の濃さと数字で並べる。
- 【暫定】（2026-11-07 の試作）時間帯の図の下に、その週の傾向を一文で出す。30分のマスを2つ続けた1時間ごとの回数のうち、いちばん多いところを書く（例: 「この週は 15:00〜16:00 に多く、9回のうち 5回（4日）です。」）。週の合計が3回より少ないときと、いちばん多い1時間でも全体の3割に届かないときは、時間帯の偏りを言わない。なぜその時間かは書かない（きっかけは ABC記録で確かめる）。

#### 6.4.3 ABC分析【暫定 / Phase 1】
- 【決定121】名前は「ABC分析」とする（もとは「ABC集計」。発注者回答 2026-11-07）。
- 先行事象別・結果別・場面別（場所・活動）・状況要因別の生起数を多い順に並べる。
- 【決定71】「関わった人」は所属ごと（家族 / 施設の職員 / 学校の先生）にまとめて数え、個人名のランキングは出さない（6.10 の「責任追及に使える表示は作らない」と合わせるため）。
- 記録者が付けた機能仮説の分布。
- 行動と期間（直近2週間・支援開始から・指定）を選ぶ。グラフ画面の「ABC分析」から開く。
- AIの要約入力に使う（6.5）。
- 【決定72 / Phase 3】AI のまとめ: AI あり のチームだけ、集計の上に「AI のまとめ」を出す。集計を短い文章にするだけで、機能の判断や支援の方法は書かない（それは 6.5 の AI分析が行う）。作るたびに AI の回数を1回使う（14.2 #36）。仮名化などの条件は 6.5 と同じ。
- 【暫定】（2026-11-05 の試作）AI のまとめに送るのは、行動名・期間・ABC記録の件数と、きっかけ・結果・場面・状況要因・関わった人（所属）の件数だけ（名前は置きかえる）。記録者の機能の見立ての集計は送らない。返ってきた文が300字を超えるか、「機能」「注目」「回避」「すべき」「しましょう」など機能の判断や助言にあたる語を含むときは捨てて作り直す。まとめは行動と期間ごとに保存し、作り直すと新しいものを出す。AI の残り回数はチームの分（月300回・1日30回）と自分の分を出し、どちらかが0なら押せない。開発用の「見本の結果」は回数に数えない。

#### 6.4.4 「できたこと」の可視化【暫定 / Phase 1】
- 望ましい行動・代替行動の増加や、問題行動のない日の連続記録をホームで強調表示する。ガイダンス「チームの微々たる成果を日々褒め称える」を UI で担保する。
- 【決定】「できたこと」の文は、記録の集計に定型文を当てはめるルールベースで生成し、外部の AI API は使わない（AI なしモードでも表示され、オフラインでも動く）。AI ありモードでも同じ定型文のままにし、AI の役割は機能仮説と代替行動の提案に限定する。
- 【暫定】判定条件の例: 代替行動の日次回数が3日連続で前日以上 / 問題行動が0の時間帯が週4日以上 / 7日平均が達成基準を下回った / 平均強度が2週間で1段階以上低下。しきい値は実装時に専門家と決める。
- 【決定51】過去の「できたこと」を見返す画面（日付・場所付きの一覧）は Phase 2 で作り、支援会議でも使う。Phase 1 はホームの表示だけ。
- 【暫定】（2026-11-05 の試作）判定の決まり（しきい値は専門家と決め直す）: (1) 代替行動・望ましい行動（回数で記録）の1日の回数が3日続けて前の日と同じか増え、その間に増えている。(2) 問題行動のない午前（12時より前）か午後が、直近7日で4日以上（その時間帯に何か記録がある日だけ数える）。(3) 直近7日の平均が、実施中の支援計画の達成基準に届いた。(4) 平均の強度が、前の7日より直近7日で1段階以上下がった。同じことが続く間は、届いた最初の日だけに出す。場所は、その間にいちばん多く記録された場所の名前。
- 【暫定】（2026-11-07 の試作）判定の決まりに (5) を足す: 代替行動・望ましい行動（回数で記録）の1日の回数が、これまでのどの日よりも多くなった（それより前に記録のある日が7日以上あり、2回以上のとき）。文は「「休憩カードを渡す」が、初めて1日6回になりました」。増えるたびに出る。
- 【暫定】（2026-11-05 の試作）ホームには直近7日の「できたこと」を3つまで出し、「すべて見る」から一覧（月ごと、場所で絞り込み）を開く。一覧は計画の画面からも開ける。

### 6.5 AI機能分析補助【決定（機能）／設計は暫定】
- 入力: 行動定義、期間内の ABC記録、クイック記録の集計、場面・状況要因、支援者メモ（仮名化済み）。
  - 【暫定】（2026-11-07 の試作）支援者メモは、ABC記録1件ごとの「メモ」を、名前を置きかえてから1件200文字まで送る（A・C の自由記述はこれまでどおり）。
- 出力（構造化）:
  1. 推定される機能（注目 / 要求 / 回避・逃避 / 感覚）を根拠となる記録の件数・傾向とともに提示。複数機能の併存も可。
  2. 確信度（高・中・低）と、その理由。
  3. 仮説を絞り込むために「次に観察すべきこと」「記録に追加すべき項目」。
  4. 問題行動が起きやすい条件・起きにくい条件の要約。
- 【決定】出力は常に「AIによる仮説（支援者の確認が必要）」と表示し、支援者が「採用 / 修正して採用 / 却下」を選んで初めて支援計画に紐づく（支援計画のない Phase 1b では「採用した仮説」として保存する。4章）。
- 【暫定】記録が一定数（例: ABC記録 10件）未満の場合は「データ不足」と返し、推定しない。
- 【暫定】AI補助の対象は、間接的アセスメントと ABC記録に基づく**記述的な機能的アセスメント**の段階とする。随伴性操作による実験的機能分析（直接的アセスメント）は専門家が実施する前提。【決定49】実験的機能分析の条件別記録枠はアプリに用意しない。
- 【決定50】観察者間一致（2人の同時記録の照合）を確かめる機能は作らない。判断のずれは、操作的定義と強度の基準を画面に示すことで減らす（決定23）。
- 【暫定】AI出力と採否の履歴を保存する（責任の所在と後からの検証のため）。
- 【暫定】試用期間はハッカソンで得た API クレジット（500ドル分）を使い、使い切らないよう利用上限を設ける（14.2 #36）。「AI で分析する」「代替行動を提案してもらう」を1回押すごとに1回と数える。
- 【決定63】AI を使える人: 分析・提案は支援者も実行できる。採否を決めるのは管理者・副管理者・支援リーダー。閲覧者は結果と採否を見るだけ。
- 【決定63】1人ごとの上限: 管理者・副管理者・支援リーダーは1人 月100回・1日10回、支援者は1人 月30回・1日3回。どの人の分もチームの上限（月300回・1日30回、決定60）に含まれる。上限に近づくと残り回数を表示する。
- 【決定94】分析・提案の結果と採否は、同期でチームのメンバー全員に届く（決定63 の「閲覧者は結果と採否を見るだけ」、決定70 の「採用したもの」の一覧を、ほかのメンバーの端末でも見られるようにするため）。サーバーに入るのは AI に送った仮名化した内容と AI が返した内容だけで、写真は入らない。役割の決まりはサーバーでも強制する: 入れられるのは支援者以上（入れた人は自分）、採否を決められるのは支援リーダー以上で1回だけ（決めた人と時刻はサーバーが書く）、結果の中身は誰も書きかえられず、消すこともできない。

### 6.6 AI代替行動・先行子操作の提案【決定（機能）／設計は暫定】
- 採用された機能仮説に基づき、次を提案する:
  1. 機能等価な代替行動の候補（例: 回避機能 → 「休憩カード」の要求、注目機能 → 「呼びかけ」のスキル）と、その教え方・プロンプトの出し方。
  2. 先行子操作（活動スケジュール、選択肢提示、視覚的支援、課題の修正、非随伴性強化、きっかけとなる嫌悪刺激の除去）。
  3. 望ましい行動の強化方法（既存のレパートリーで頻度が少ないものを優先）。
  4. 対象者の「好きなもの」リストを強化子候補として活用する。
- 【暫定】（2026-11-07）4 のため、提案を頼むときに好きなもの（6.14）の名前・種類・ハマり度だけを送る。隠したもの・消したものは送らず、ハマり度の高い順に20件まで。名前は記録と同じように置きかえてから送る。写真と「使い方と注意」のメモは送らない。AI には「好きなものを取り上げる・お預けにする使い方は書かない」と指示する。
- 【決定・絶対条件】**罰・弱化・嫌悪刺激・身体拘束・隔離・叱責を提案しない。** システムプロンプトで禁止し、出力後にも語句フィルタと人によるレビューで二重に防ぐ。該当表現が検出された場合は出力を破棄して再生成する。
- 【決定】医療・服薬・診断に関する助言はしない（主治医への相談を促す定型文のみ）。
- 【暫定】提案は「候補」であり、支援者が編集して支援計画に取り込む（Phase 1b では「採用した案」として保存し、Phase 2 で計画に取り込む。4章）。採用率をログとして記録し、提案品質の改善に使う。
  - 【暫定】（2026-11-07 の試作）AI の画面の「採用したもの」の下に、仮説と提案それぞれの採用率（採用・修正して採用・却下の件数。未決定は数えない）を出す。採否はすでに記録に残っているので、新しい記録は作らない。

### 6.7 行動支援計画（BSP）【決定（機能）／Phase 2】
- 項目: 標的行動（問題行動・望ましい行動・代替行動）、機能仮説、支援目標、達成基準（数値と期限）、先行子操作、結果操作（強化の方法）、プロンプトの方法、危機時の対応手順、見直し日、担当。
- 【決定】（決定121）画面では、むずかしい用語を言いかえる。「先行子操作」は「先にできる工夫（予防）」、「プロンプト」は「手助け（手助けの出し方）」と書く。仕様書の中では、これまでの用語も使う。
- 【決定】機能仮説を選ぶと、代替行動欄に機能別の定型ヒントを1行表示する（AI なしモードでも表示）:
  - 回避・逃避: 「休みたい」「手伝って」と伝える方法を教える
  - 注目: 「見て」「ねえねえ」と適切に呼ぶ方法を教える
  - 要求: 「貸して」「ちょうだい」と伝える方法、または「待つ」方法を教える
  - 感覚: 同じ感覚を安全に得られる別の活動を用意する
- 【暫定】ヒントは編集可能な定型文としてアプリ内に持ち、AI ありモードでは AI 提案の土台として使う。
- 【決定】支援目標は複数の関係者の合意で決める。合意者（家族・施設・学校など）の確認（サインオフ）を記録する。
- 【決定】達成基準に達したらレパートリー拡大、一定期間未達なら計画修正、をシステムが促す（見直し日の通知と、グラフと達成基準線の比較）。
- 【暫定】（2026-11-07 の試作）達成基準ごとに「続ける期間」（直近7日で見る・2週連続・3週連続・4週連続）を選べる。7日ごとの平均（今日までの7日、その前の7日…）が続けて届いた週を数え、「1週目達成」「2週連続で達成」のように出す（ワイヤーフレーム「計画」）。記録のない週があると、そこで数え直す。
- 【決定67】支援計画は1つの計画を上書きして保存し、変更の履歴を残す（版を分けて並べることはしない）。変更が実施中になった日は、グラフのフェーズ線に自動で反映する。
- 改訂（変更）と合意の決まり（ワイヤーフレーム「24 支援計画の変更履歴」「25 支援計画の合意」）:
  - 【決定67】保存すると計画は上書きされ、変更の履歴に「いつ・誰が・どの項目を・前は何で今は何に・なぜ変えたか」が残る。履歴は誰も書きかえ・削除できない。【暫定】「変えた理由」は必ず書く。前の内容に戻すときは、履歴から前の内容を写して保存する（これも1回の変更として残る）。
  - 【暫定】履歴の画面では、変更ごとに日付・変えた理由・保存した人・変わった項目（前と今）・合意の人数を新しい順に並べる。
  - 【決定69】変更を保存すると「合意待ち」になる。合意者は、保存した人が変更ごとに管理者・副管理者・支援リーダー・支援者から選ぶ（閲覧者は選べない）。管理者は必ず入る。
  - 【決定75】合意の依頼と「意見あり」は、通知もメールも送らない。頼まれた人がアプリを開いたときに、ホームと計画の画面に「確認の依頼があります」と出す。「意見あり」も、保存した人と管理者が計画の画面を開いたときに出す。
  - 【決定68】家族（管理者。管理者が操作できないときや引き継ぎ中は副管理者でもよい）が合意した日から変更後の計画が「実施中」になり、その日がグラフの縦線（フェーズの切り替え）になる。それまでは変更前の計画が実施中のまま。ほかの人の合意は待たず、まだの人は「未確認」と出す。
  - 【決定69】頼まれた人は「この内容で合意する」か「意見を送る（今は合意しない）」を選ぶ。意見を送ると「意見あり」と出る。合意したあとでも、意見を送れば「意見あり」に変わる。
  - 【暫定】保存した人が合意者でもある場合は、保存と同時に合意したものとする。合意待ちの変更は、保存した人と管理者・副管理者が取り下げられる（取り下げも履歴に残る）。
  - 【決定69】合意はチームの中で「内容を確かめた」という記録で、日時・人・役割・どの変更への合意かを残す。施設の個別支援計画書などへの署名の代わりにはしない（決定57）。
- 【暫定】「制限的な対応」を計画に書く場合は、最も制限の少ない方法から順次導入すること、データに基づく定期見直しを必須項目にする。
- 【暫定】（2026-11-05 の試作）合意待ちの変更があるときに次の変更を保存すると、前の合意待ちの変更は「新しい変更に置きかわった」として閉じ、新しい変更の合意を待つ（履歴には両方が残る）。
- 【暫定】（2026-11-05 の試作）試作では、変更を実施中にできるのは管理者の合意だけにする。管理者が操作できないときに副管理者が代わる流れ（決定68）は、ログインと引き継ぎができてから作る（引き継ぎは 2026-11-07 に作った）。
- 【決定92】副管理者は、合意の画面の「管理者の代わりに合意する」で、合意待ちの変更を今日から実施中にできる（決定68）。「管理者が操作できないとき」かどうかはアプリでは判断できないので、使うかどうかは副管理者が決める。ふだんの「合意する」では、副管理者が合意しても実施中にならない。代わったときは、変更履歴と合意の画面に「副管理者の〇〇が管理者の代わりに合意」と出し、管理者の返事は「未確認」のまま残す。サーバーでも、実施中にできるのは管理者と副管理者だけ（0015）。
- 【暫定】（2026-11-05 の試作）計画の画面では、達成基準ごとに直近7日の平均と「達成・未達」を出し、見直し日の7日前から画面に知らせる（通知は出さない）。計画の画面から、変更履歴・合意・支援会議メモ・できたこと・身体拘束の記録・PDF レポートを開く。
- 【決定93】達成基準の「期限」は基準ごとに入れられる（入れなくてもよい）。期限を過ぎても未達のときは、計画の画面のその基準の下に「期限を過ぎても届いていません。グラフを見て、計画を見直しましょう」と出す（決定「一定期間未達なら計画修正を促す」の「一定期間」を期限で表す）。達成しているときは「届いています。できることを広げましょう」と出す。通知は出さない。
- 【決定90】計画の画面に「機能分析のツール」を置き、井上研究室の「機能分析スクリーニングツール日本版」（外部のサイト、6.13）へのリンクを、機能の仮説を考えるときに支援者が使えるツールとして紹介する。計画があってもなくても出す。
- 【暫定】（2026-11-07 の試作）計画の項目に「場面」（この計画を使うところ。例: 施設・学校の個別課題の時間）を足した。前に保存した計画では空のまま。
- 【暫定】（2026-11-07 の試作）合意待ちの変更に、まだ合意していない人がいるときは、計画の画面に「確認を依頼する」を出す（ワイヤーフレーム 4）。押すと端末の共有メニュー（LINE・メールなど）で、合意の画面へのリンクを送る。共有メニューがない端末では、依頼の文とリンクをコピーする。文には対象者の名前や計画の中身を入れない（送り先のアプリに残るため）。アプリからは通知もメールも送らない（決定75）。

### 6.8 危機対応・身体拘束記録【決定（機能）／Phase 2】
- 緊急やむを得ない身体拘束が発生した場合の専用記録。治療ではないことを画面に明示。
- 項目: 日時、状況、3要件の確認（切迫性・非代替性・一時性）それぞれの根拠、実施者、判断者（組織的判断）、開始・終了時刻、本人の状態、事後の組織的検討、家族への報告の有無。
- 【暫定】拘束記録が一定回数を超えた場合、計画見直しをアラートする。【決定64】見直しをすすめる目安は、管理者・副管理者がチームの設定で自由に決められる（期間: 1週間 / 1か月 / 3か月、件数: 0件から。0件なら1件でも記録されたらすすめる）。【決定74】目安の初期値は置かない。拘束記録を初めて使うとき（拘束記録の画面とチームの設定）に、管理者・副管理者が期間と件数を決める。決めるまでは件数だけを表示し、見直しはすすめない。そのことを画面に「目安が未設定です」と出す。変更は監査ログに残す。拘束記録の画面に、その期間の件数と目安を出す。
- 【暫定】拘束記録を入力できるのは支援者以上。保存後の修正は、記録した人と管理者・副管理者・支援リーダーができ、修正の履歴が残る。虐待防止の証拠として、拘束記録は取り消し・削除できない（行動の記録ごと削除の対象にも含めない）。「あとの組織での検討」は後から追記する欄とする。
- 【決定】AIは身体拘束を提案しない。拘束記録はAIの提案入力には「頻度の事実」としてのみ使い、手法として学習・推奨しない。
- 【暫定】（2026-11-05 の試作）拘束記録の画面は計画の画面から開く。画面の上に「治療や支援の方法ではありません」と出す。3要件はそれぞれ「確認した」の印と根拠の欄を置き、印がそろわなくても行ったことはそのまま記録する（そろわないときは「チームで必ず検討してください」と出す）。初めて保存するときは「保存すると消せません」と確かめる。一覧には、3要件の確認・家族への報告・あとの組織での検討があるかを出す。
- 【決定】（決定119）ホームに「身体拘束を記録する」を置き、拘束記録の入力画面を開く（計画の画面からも開ける）。問題行動の +1 とは分ける。
- 【決定】（決定119）その場の入力は負担を減らす: 3要件はチェックだけにし、根拠の欄・判断者・あとの組織での検討は出さない。これらは保存した記録を開いたときに、あとから書き足せる（データの項目は残す。決定10 の「組織的判断を記録する」は、あとから書き足す形にした）。
- 【決定】（決定119）グラフの画面に「身体拘束」の専用のパネルを出す（1日の回数と合計時間［分］。記録のある日だけ点を打ち、記録のない日は 0 にしない）。拘束記録が1件もない対象者では出さない。時間帯の図でも、行動と同じように「身体拘束」を選べる（始めた時刻のマスに回数）。
- 【暫定】（2026-11-05 の試作）見直しの目安は、拘束記録の画面とチームの設定の両方から決められる。
- 【暫定】（2026-11-05 の試作）試作の AI（6.5・6.6）には、拘束記録をまだ送らない。
- 【暫定】（2026-11-05 の試作）「記録ごと削除の対象に含めない」は、行動を記録ごと削除するとき（決定38）の話とする。チームの削除（14.2 #42）では、端末の中からは、ほかの記録と同じく拘束記録も消す。【暫定】（2026-11-07 の試作）サーバーでは、虐待防止の証拠として残すべきか（14.3 #11）が決まるまで消さずに残す（メンバーがいなくなるので、誰も読めない）。

### 6.9 チーム・共有【決定（機能）／詳細は暫定】
- 対象者ごとのサポートチームに、メール / 招待リンク / QRコードで参加者を招待する。
- 【決定44】アプリは一般公開せず、関係者だけが使う。
  - 新規登録は招待リンク（メール・QR を含む）からだけ。招待のない人はログイン画面を開けても登録できない。
  - 【暫定】（2026-11-07 の試作）アカウントを作る画面で、使える招待コードか開始コードを入れないと作れない。画面だけでなくサーバー（Supabase のアカウントを作る直前の確認）でも断る。コードはこの時点では使い切らず、チームを作る・チームに入るときに使い切る。Supabase の管理画面から運営が直接アカウントを作るときは、この確認が働かないので使わない。
  - 【決定97】招待リンクを開いたとき、ログインの前に見せるのは「役割・招待した人の名前・有効期限」だけ。チームの名前（対象者の呼び名）は、ログインしてから見せる（ワイヤーフレーム「ログイン / 招待受諾」）。開始コードのときは、種類と期限だけ。サーバーの `invite_preview`（マイグレーション 0019）が、ログインしているかどうかで出す中身を変える。
  - 【決定】（決定120）招待された人は、アカウントを作る画面と、はじめの画面のコードの欄で「QR を読む」を押し、招待した人のスマホに出ている QR をカメラで読める。読めたらコードの欄に入る（カメラの映像は端末の中だけで読み、保存も送信もしない）。
  - 【決定】（決定120）スマホのアプリ（iPhone・Android）の中では、相手が開ける招待リンクの住所がないので、リンクの代わりに「招待コードと入れる場所」の文を端末の共有メニューで送り、QR にもコードを入れる。ブラウザでは今までどおりリンクを送り、QR にもリンクを入れる。「QR を読む」はどちらの QR も読める。計画の「確認を依頼する」も、アプリの中ではリンクを付けずに文だけ送る。
  - 弱いところ: コードが使えるかどうかは、ログインしていなくても確かめられる（アカウントを作る前に知らせるため）。コードは読み違えにくい32種の文字で10文字あり、当てずっぽうで当たることはまず無いが、試す回数の制限はしていない。
  - 新しいチーム（新しい対象者）を作るには、運営が発行する「開始コード」が要る。コードは試用に参加する家族にだけ渡す。
  - 【暫定】開始コードは1つで1チームを作れる使い切りで、有効期限は発行から30日。運営はいつでも無効にできる。きょうだい2人なら2つ渡す。
  - サイト自体を関係者以外に見せない仕組み（Cloudflare Access など）は任意とし、Phase 1 では使わない。
  - Phase 2 のストア配布も一般公開しない（iPhone は TestFlight または非表示配布、Android はクローズドテスト）。
- 【暫定】（2026-11-07 の試作）メンバーに「職種」（例: サービス管理責任者・支援員・担任。40文字まで）を付けられる。メンバー一覧に「所属 ・ 職種」で出す。書きかえられるのは、メンバーを直せる人（支援リーダー以上）。役割（権限）とは別で、職種で権限は変わらない（マイグレーション 0019）。
- 【決定】役割の名前の意味:
  - **管理者（保護者）**: アプリとデータの管理者。対象者の記録の所有者で、チームに1名。保護者（本人が使える場合は本人）がなる。
  - **副管理者**: 管理者の代わりができる家族・後見人。管理者に何かあったときに引き継ぐ。
  - **支援リーダー**: 相談員・施設のサービス管理責任者など、支援の中心になる専門職。行動定義と支援計画を編集し、招待もできるが、記録の削除と管理者の変更はできない。
  - **支援者**: 記録する人（職員・教員・家族）。
  - **閲覧者**: 見るだけの人。
- 役割【暫定】:
  | 役割 | 対象者設定 | 行動定義 | 記録 | 閲覧 | 支援計画編集 | 招待・権限 | 削除 |
  |---|---|---|---|---|---|---|---|
  | 管理者（保護者・本人） | ○ | ○ | ○ | ○ | ○ | ○ | ○ |
  | 副管理者（家族・後見人から1名） | ○ | ○ | ○ | ○ | ○ | ○ | × |
  | 支援リーダー（相談員・管理職） | ○ | ○ | ○ | ○ | ○ | ○ | × |
  | 支援者（職員・教員・家族） | × | 提案 | ○ | ○ | 提案 | × | × |
  | 閲覧者 | × | × | × | ○ | × | × | × |

  「削除」は行動の記録ごと削除（6.2）を指す。管理者のみで、施設・学校側は非表示まで。
  役割とは別に、管理者はメンバーに「家族」の印と「睡眠の入力を許可」を付けられる。睡眠ログの入力・変更は管理者・副管理者・家族の印のある人・許可された人のみ（6.3.4）。強化子リストの編集は支援者以上。
- 【暫定】（2026-11-07 の試作）表の「提案」は、行動の一覧と支援計画の画面の「提案」の欄から、文で出す（行動への提案は、どの行動かを選ぶ）。採用か見送りを決めるのは管理者・副管理者・支援リーダーで、1回だけ決められる（決めた人と時刻はサーバーが書く）。採用しても行動や計画は自動では変わらず、採用した人が編集して反映する。提案の文は誰も書きかえられず、消せない。提案の通知は出さず、画面に出すだけ（決定75 と同じ）。閲覧者は見るだけ。サーバーでも同じ決まりを強制する（マイグレーション 0017）。
- 【決定】管理者は、家族または後見人から**副管理者**を1名指名できる（推奨）。副管理者は管理者とほぼ同じ権限を持つが、記録ごと削除と管理者の変更はできない。
- 【暫定】管理者の引き継ぎ:
  - 管理者が自分で引き継ぐ: 設定から副管理者（または家族の印のあるメンバー）を新しい管理者に指名し、相手が受諾したら交代する。
  - 管理者が操作できない（高齢・入院・死亡など）: 副管理者が「管理者の引き継ぎ」を申請する。管理者に通知し、14日間管理者から応答がなければ副管理者が管理者になる。期間中に管理者がログインして拒否すれば取り消される。
  - 副管理者がいない場合: 後見人や家族が本人確認書類と関係を示す書類を運営窓口に出し、運営側が確認して管理者を変更する。
  - 本人が成人してアプリを使える場合は、本人を管理者にする引き継ぎもできる。
  - 引き継ぎの申請・応答・交代はすべて監査ログに残し、チームの支援リーダーにも通知する。
  - 引き継ぎ中もチームの記録・閲覧は止まらない。
- 【暫定】（2026-11-07 の試作、決定88）管理者の引き継ぎを、チーム画面の「管理者の引き継ぎ」に作った（ログインして共有する版だけ）:
  - 管理者は、副管理者か「家族」の印のある人（承認済みで停止されていない人）を選んで「引き継ぎをお願いする」。相手は「受けて管理者になる」か「断る」を選ぶ。管理者は返事の前なら取り下げられる。
  - 副管理者は「管理者になる申し込みをする」。管理者は14日の期限の前なら「断る」、いつでも「いま引き継ぐ」を選べる。期限を過ぎて断られていなければ、副管理者の端末が次の同期で管理者になる（「管理者になる」のボタンもある）。申し込んだ副管理者は取り下げられる。
  - 入れかわったあと、元の管理者は副管理者になる。ほかにもう副管理者がいるときは支援リーダーになる（副管理者は1人、決定39）。
  - 進んでいる引き継ぎはチームに1つだけ。受けるときにも、相手がまだ管理者になれる人か（停止されていない・外れていない・役割が変わっていない）をサーバーで確かめる。
  - メールでの通知はまだないため、返事が要る人（指名された人、申し込まれた管理者）と、かかわっていない支援リーダー以上の人には、ホームとチーム画面にお知らせを出す。
  - 管理者の役割は、サーバーの引き継ぎの関数の中からだけ変えられる（行レベルセキュリティとトリガーで守る。マイグレーション 0012）。お願い・返事・入れかわりは、サーバーの監査ログに残る。
  - 運営窓口での変更と、本人を管理者にする引き継ぎはアプリの外（本人のアカウントは今は作らない、決定54）。
- 【暫定】法人（施設）単位のアカウント管理は MVP に含めない（個人利用で検証するため）。
- 【暫定】法人をまたぐ共有時の閲覧範囲は MVP ではチーム内全員同一。記録ごとの公開範囲（例: 施設内の申し送りメモは学校に見せない）は Phase 2 以降。

- 【暫定】（2026-11-05 の試作）「チームの設定」画面（ワイヤーフレーム 13）は、チーム画面の「同意と設定」から開く。AI の あり／なし（管理者）、睡眠不足の判定（「いつもより2時間以上短い夜」か「5〜8時間未満」、管理者・副管理者）、CSV の書き出し、チームの削除（管理者）を置く。多要素認証の基準（管理者、7.4.3）もここに置く。書き出したときの管理者へのメールは、まだない（決定101: 今回はメールを使わない）。かわりに、1人が1日に3回以上書き出した日は、管理者の画面の上に知らせる（決定103、7.4.2 #6）。身体拘束の見直しの目安（管理者・副管理者、6.8）もここに置く。
- 【暫定】（2026-11-05 の試作）チームの削除は申し込みから30日間取り消せ、30日たってアプリを開いたときに、その対象者の記録・写真・場所などを消す。監査ログは「誰も消せない」（7.4.2 #6）ため残し、削除したことを書き足す（扱いは 14.3 #10 で確認）。
- 【暫定】（2026-11-07 の試作）サーバーで使っているチームは、30日たってチームのだれか（役割は問わない。決めたのは管理者）がアプリを開いたときに、先にサーバーで消す（0023）。30日たったかはサーバーの時計で確かめ、サーバーで消せなかったとき（電波がない・30日にまだならない）は端末の中も消さずに、次に開いたときにもう一度試す。サーバーでは記録・写真・場所・メンバー・設定などを消し、対象者の行は名前などを消して「削除したチーム」として残す（監査ログがこの行を指すため）。監査ログ（14.3 #10）と身体拘束の記録（14.3 #11）は、扱いが決まるまで残す。ほかのメンバーの端末は、次の同期でそのチームのデータを消す。30日たっても誰も開かなければサーバーに残る（決まった時刻に自動で消すしくみは、外部の設定が要るので、まだない）。
- 【暫定】（2026-11-05 の試作）「家族」の印と「睡眠の入力を許可」は、チーム画面のメンバーの「変更」から管理者が付け外しする。
- 【暫定】（2026-11-06 の試作）役割の変更と停止（7.4.2 #2）:
  - 管理者・副管理者・支援リーダーは、チーム画面のメンバーの「変更」から、ほかのメンバーの役割（閲覧者・支援者・支援リーダー）を変えたり、停止したり、停止を外したりできる。副管理者にすることと、副管理者の行を変えることは管理者だけ。管理者の役割は変えられない（引き継ぎは上の手順）。
  - 自分を停止することはできない（管理者が自分を止めると、元に戻せる人がいなくなるため）。この決まりはサーバーで守る。
  - 停止すると、その時点からサーバーのそのチームのデータを読むことも書くこともできなくなる（行レベルセキュリティ）。停止された人の端末は、次に通信したときにそのチームのデータ（監査ログの写しを含む）を消し、「チームでの利用が止められました」と出す。
  - まだできていないこと: ログインそのものを切ること（いまはログインしたままでもチームのものは何も見えない）と、所属でまとめて停止すること。所属は「家族・学校・施設」などの種類しか持っていないため、施設名・学校名で絞るには所属の名前を足す必要がある。

### 6.14 強化子リスト（好きなもの）【決定（機能）／詳細は暫定 / Phase 1】

- 【暫定】そのやり方として、長辺 640px の JPEG を文字（data URL）にして、サーバーの写真の表の1つの欄に入れる（1枚 約40万文字まで）。

#### 6.14a 写真のプライバシー【暫定（14.2 #34）】
- 写真の対象は物・活動・場所に限る。本人や他の人の顔は写さない方針を撮影画面に表示し、同意事項にも含める。アプリが顔を自動で見分けて止めることはしない（方針と確認で担保する）。
- 写真はチーム内だけで閲覧でき、CSV / PDF のエクスポートには含めない。AI あり モードでも写真は送信しない。
- 写真は暗号化して保存し、強化子を削除すると写真も削除する。保存期間は記録本体と同じ（決定56: 使っている間は自動で消さない）。
- 画像の位置情報（Exif）は保存時に除去する。

### 6.15 手順と手順のチェック（課題分析）【決定（機能）／詳細は暫定】
- 【決定123】望ましい行動・代替行動に、その行動を小さなステップに分けた「手順」（課題分析）を付けられるようにし、ステップごとに要った手助けを記録する「手順のチェック」（データシート）を作る。Phase を待たずに今作る（発注者回答 2026-11-08）。文献と考え方は `docs/課題分析（手順）の提案.md`。
- 【暫定】「手順」は強度と同じ付加項目で、問題行動には付けない。行動の測定方法（6.2、決定17）は変えず、手順のチェックは別の記録として持つ。
- 【暫定】手順の中身: ステップは 2〜9 個。各ステップは「本人の動き」1つ（短い文、60文字まで）と、任意の「支援者の動き・留意点」（100文字まで）。教える順番は 前から／後ろから／全部通して（既定は全部通して）。最初から「本人が手助けを嫌がったら手を離して中断し、『途中でやめた』で記録する」の留意点を入れておく（消せる）。
- 【決定127】手順を作る・変えるのも、チェックするのも支援者以上。閲覧者は見るだけ（発注者回答 2026-11-08）。【暫定】チェックの取り消し・直しは +1 と同じ（記録した本人と、支援リーダー以上。6.3.5）。
- 【暫定】手順を変えると版を1つ上げ、古いチェックは古い版のステップ文のまま残す。グラフには「手順の変更」の点線を引く。
- 【決定125】手助けは4段階: 一人で／声かけ・指さし／手本／手を添えて（発注者回答 2026-11-08）。【暫定】ほかに小さく「機会なし」（その日はそのステップをする場面がなかった）を置き、割合の分母から外す。画面の上の「途中でやめた」をオンにすると、まだ付けていないステップは「やめた」になり、分母に残す（嫌がって中断したステップを「できた」と数えないため）。
- 【暫定】「一人でできた割合」=「一人で」の数 ÷（ステップ数 − 機会なし）。保存したあとに直す画面は作らず、まちがえたときは「取消」して付け直す（2026-11-08 の試作）。
- 【決定135】手順のチェックの画面には、日時・場所・本人の様子（メモ）の欄を置かない。日時は保存した時、場所はホームで選んでいる場所が自動で入る（発注者回答 2026-11-08）。
- 【決定132】チェックは、ホームの行動カードにある小さな「手順」から開く。カードの高さは増やさない。【決定136】「手順」は、カードの右上ではなく行動の名前のすぐ後ろに置く（発注者回答 2026-11-08。決定132 の「右上（−1 の左）」を変更）。【暫定】名前が長いときは、名前に続けて次の行に回る。カードのほかの場所を押すと、これまでどおり +1 になる。今日のチェックの回数と取り消しは、ホームではなく手順のチェックの画面に出す（発注者回答 2026-11-08）。【暫定】取り消すのは、いちばん新しいチェック1件（−1 と同じ決まり、6.3.1）。取り消しは論理削除で、監査ログに残り、「元に戻す」で戻せる。
- 【決定134】手順のチェックで全部の手順が「一人で」だった回は、その行動の +1（記録）を同じ日時・場所で自動で作る。保存した画面に「+1 しました。ホームの ＋ は押さなくて大丈夫です」と出す。チェックを取り消すと、その +1 も一緒に取り消し、「元に戻す」で一緒に戻す（発注者回答 2026-11-08。決定124「+1 は自動で作らない」を変更）。
  - 【暫定】+1 を作るのは、記録のしかたが「回数」の行動だけ。途中でやめた回は作らない。「機会なし」の手順は数えず、残りが全部「一人で」なら作る。一人でできなかった回は +1 を作らない（ホームの回数が水増しにならないようにするため）。
  - 【暫定】ホームの −1 で、自動で付いた +1 だけを取り消したときは、手順のチェックは残る（チェックを取り消しても、もう +1 は無いので何も起きない）。
  - AI 分析（6.5）には手順のチェックそのものは送らない（できた回の +1 は、ふつうの記録として送られる）。
- 【決定126】達成の目安は「一人でできた割合が X% 以上の回が N 回連続」。既定は 100% × 3回で、割合と回数は手順ごとに自由に決められる（発注者回答 2026-11-08）。【暫定】割合は 50〜100%、回数は 1〜10回。
- 【暫定】グラフ（6.4.1）に「一人でできた割合」のパネルを足す（1日の平均、記録のない日は 0 にしない）。その下に「ステップ × 回」の表を出し、マスの色と文字で手助けの段階を示して、どのステップで止まっているかを見られるようにする。
- 【暫定】支援計画（6.7）の達成基準に、新しい種類「手順の自立率」を足す。決まりは手順の達成の目安と同じ「X% 以上が N 回連続」で、計画の画面に直近の回の割合を出す。期限の扱いはほかの基準と同じ（決定93）。
- 【決定130】「できたこと」（6.4.4）に手順の決まりを2つ足す（発注者回答 2026-11-08）。① 一人でできた割合が初めて 100% になった。② 一人でできた割合が3回続けて前の回以上で、その間に上がった。【暫定】文の例:「『休憩カードを渡す』の手順を、初めて全部一人でできました」「『休憩カードを渡す』の手順で、一人でできる所が増えています（40% → 80%）」。
- 【暫定】AI ありのチームでは、手順の編集画面に「AI に下書きを頼む」を置く（Phase 1b）。送るのは、仮名化した行動の名前・定義・種類、代替行動なら元の問題行動の名前と機能、すでにある望ましい行動・代替行動の名前だけ。返すのは、ステップ（7個まで、各ステップに本人の動きと支援者の動き・留意点）、はじめに手助けが多く要りそうなステップ、準備するもの、教える順番の案と理由、注意（「嫌がったら手を離して中断」を必ず含める）。結果は「AI の案」と表示し、人が直して保存して初めて手順になる。
- 【決定128】AI の下書きに、対象者の「特性メモ」と「苦手なこと・気をつけること」は送らない（自由に書く欄で、仮名に置きかえられない言葉が混じるおそれがあるため。発注者回答 2026-11-08）。
- 【決定129】AI の下書きは、AI の回数の上限（決定60・63）の「提案」1回として数える（発注者回答 2026-11-08）。【暫定】実行できる人・回数の数え方は提案と同じ。
- 【暫定】禁止語（9章）に加え、手順の下書きだけに「押さえ」「抑え」「制止」「無理に」「引っ張」「羽交い」「閉じ込め」を足す（手を添える手助けと身体拘束の境目を越えさせないため）。見つけたら結果を捨てて、もう一度作らせる。
- 【決定131】AI の手順の下書きでは、問題行動が起きた直後に代替行動を促したり、休みなどを与えたりする書き方をさせない（問題行動が代替行動につながる流れの最初の一歩として身につくのを防ぐため）。促すのは問題行動の前ぶれのときや落ち着いた場面にする。問題行動が起きたときについては安全を守ることだけを書かせ、「反応しない」とは書かせない（計画的無視は決定76 のとおり提案しない）（発注者回答 2026-11-08）。
- 【暫定】（2026-11-08 の試作）サーバーは手順の下書きを ai_runs に「提案」として記録する（回数の上限を数えるため）。下書きの中身は端末の中だけに暗号化して残し、同期しない。「この案を下の欄に入れる」を押しても保存はされず、人が確かめて「保存」して初めて手順になる。欄に入れるとき、メモに「嫌がったら手を離して中断」と準備するものを足す。
- 【暫定】データ: 新しい表 TaskAnalysis と StepCheck（8章）。どちらも RLS でチームを分け、「他チームのデータを読めない・書けない」テストを付ける（マイグレーション 0026。ほかのチームの行動・手順は指せず、手順は問題行動には作れない）。削除は論理削除、変更は監査ログ。電波がなくても記録でき、あとで同期する。
- 【暫定】本人用の絵付きチェックリスト（本人が自分で付ける）と手順の写真は、Phase 3 の候補。

## 7. 非機能要件

### 7.1 使いやすさ【決定（目標）／数値は暫定】
- 記録は3タップ以内。片手操作。記録ボタンなど主要なボタンは大きく（最小 48px）。
- 【暫定】押し間違いの取り消しバッジ（−1・取消）のような補助的なボタンは、主要ボタンの邪魔をしないよう小さくし、見た目 24px・タップできる範囲 32px 以上とする（WCAG 2.2 の最小タップ範囲 24px を満たす）。補助ボタンどうしは 8px 以上離す。
- 文字は大きく、専門用語には説明を付ける（「先行事象 = 直前に起きていたこと」）。
- 初回セットアップはウィザード形式（開始コードと同意 → 対象者 → 行動を1つ定義 → 場所と「わたしのいつもの時間」（後回し可） → 最初の記録）で10分以内。招待で参加した人は、場所と「わたしのいつもの時間」だけを案内する。
- 【暫定】同意（利用規約・プライバシーポリシー・要配慮個人情報の取得、7.5）は最初のステップで、開始コードを確かめたあとに取り、日時と示した文面の版を記録する。対象者は呼び名だけを必須にし（実名不要）、登録した人が管理者になる。行動の定義は「行動の追加」と同じ画面を使う。AI は初めは「なし」で、セットアップでは切り替えない。
- 【暫定】日本語のみ。将来の多言語化を妨げない設計。

### 7.4 セキュリティ【決定（方針）／対策の詳細は暫定】

#### 7.4.1 基本方針【決定】
1. **集めない**: 実名・支援者の現在地の座標・顔写真・音声を原則として扱わない（登録場所の中心は住所と同じ扱いでチーム内のみ）。要配慮個人情報は目的（支援の記録と評価）に必要な最小限に絞る。
2. **消さない・改ざんさせない**: 記録は論理削除と監査ログで保全する。虐待防止の証拠性を守る。
3. **本人側が持つ**: データの所有者は保護者・本人。法人・学校は招待された参加者であり、退所・卒業後はアクセスが切れる。
4. **既定を安全側に**: AI は既定「なし」、MFA は既定「支援リーダー以上必須」、招待は期限付き、写真はチーム内限定。
5. **アプリで担保できることと、施設の運用で担保することを分けて明記する**（7.4.2 の「担当」列）。

- 【暫定】（2026-11-07 の試作）#1・#4 の共用の端末: ログインのときに「自分専用」か「共用」かを選び、「あなたの設定」でも変えられる。共用の端末では、ログインのあとに PIN（4〜8けたの数字）を決める。PIN はハッシュにして端末の中にだけ残し、サーバーには送らない。10分さわらなければロックし、開き直してもロックのまま。ロック中も下の画面（観察のタイマーなど）は止めない。PIN を5回続けてまちがえたら15分は入れられない。人を替えるとき・PIN を忘れたときは、ログアウトして次の人（本人）がログインし直す。画面の上に「操作中: 名前」をいつも出す。自分専用・共用のどちらでも、90日使わなければログアウトする（送れていない変更があるときは、送れるまで待つ）。
- 【暫定】（2026-11-07 の試作）#1 の遠隔ログアウト（マイグレーション 0021）: 端末は同期のたびに（5分に1回まで）「この端末でログインしている」をサーバーに残す。残すのは端末の名前（「iPhone・Safari」のように、ブラウザが教える種類から作る）、共用かどうか、初めてログインした時刻と最後に通信した時刻だけで、場所や IP は残さない。本人は「あなたの設定」で自分の端末を、管理者・副管理者・支援リーダーはメンバーのシートでその人の端末を見て、「この端末をログアウトさせる」を押せる。管理者・副管理者の端末をログアウトさせられるのは管理者だけ。ほかの人の端末をログアウトさせるには、MFA が必須の人は MFA を通したログインが要る。押すと、その端末のいまのログインをサーバーで無効にし、その端末がつながっていなくても、どのチームのデータも読めず書けなくなる。端末は次につながったときに、端末の中のチームのデータを消してログアウトし、ログイン画面で理由を知らせる（送れていない変更も消える）。その人のほかのチームのデータもその端末から消える（ログインし直せば、また取ってくる）。チームの立場で頼んだものは監査ログに残す。
- 【暫定】（2026-11-07 の試作）#5 の新しい端末からのログインの知らせ（決定62・決定101）: 同じアカウントで、初めての端末からログインがあったら、それより前からある端末の画面の上に「新しい端末からログインがありました: 端末の名前（日時）」と出す。「心当たりがある」で消え、「端末を確かめる」で「あなたの設定」の端末の一覧を開く。メールでは知らせない。
- 【暫定】（2026-11-07 の試作）「この端末からログアウト」は、この端末だけをログアウトする（同じアカウントのほかの端末はそのまま）。ほかの端末をまとめて止めたいときは「ほかの端末をすべてログアウト」を使う。
- 【決定102】#6 の閲覧の記録は、「誰が・どの日に・このチームを開いたか」を1人1チーム1日に1回だけ残す。どの画面・どの記録を見たかは残さない。
- 【決定103】#6 の異常の見張りは、書き出しの多さだけにする。1人が1日（日本の時刻）に3回以上 CSV を書き出したら、管理者の画面の上に知らせる。深夜の閲覧などほかの見張りは、今回は作らない。
- 【暫定】（2026-11-07 の試作、マイグレーション 0022）閲覧の記録と書き出しの見張りの作り:
  - 閲覧の記録: アプリでチームを開くと、その日まだ送っていなければサーバーに1行残す（通信できなければ5分ごとにもう一度）。書けるのはサーバーの関数からだけで、誰にも書きかえ・削除できない（チームの削除のときだけ消す）。見られるのは監査ログと同じく支援リーダー以上で、監査ログの画面の下に「閲覧の記録（チームを開いた日・直近30日）」として日ごとに名前を並べる。
  - 書き出しの見張り: 数えるのはサーバーで、端末が送ってきた書き出しの監査ログを、直近30日の分、1人1日ごとに数える。3回以上の日があれば、管理者がアプリを開いたときに「記録の書き出しが多い日がありました」と出す。「確かめた」で消え（その時刻までの分は、この端末では出さない）、「監査ログを見る」で監査ログを開く。メールでは知らせない。
  - 限界: 書き出しの監査ログは端末が作って送るので、手を加えたアプリで書き出しの記録を送らなかったり、時刻をずらしたりすると、数から漏れる。ふつうに使っている人が何度も書き出したことに気づくための見張りで、悪意のある人を確実に止めるものではない。
- 【決定104】#1 の端末の中の暗号化は、ほかの足りない機能を作り終えてから最後に取り組む。それまでは、端末の中のデータはスマホ・パソコンのロックと端末の保護に任せる。
- 【決定108】#1 の端末の中の暗号化は、限定版にする。暗号化するのは記録の本文と写真だけ。鍵はチームごとに1つで端末の中に置き、ログアウト・遠隔ログアウト・90日でのログアウト・チームから外れたときに、データといっしょに消す。
- 【暫定】（2026-11-07 の試作）限定版の作り:
  - 暗号化する項目: 記録の活動・場所の名前、睡眠のメモ、ABC の内容、コメント、会議メモ（場所・ほかの参加者・結果・決めたこと・グラフ・計画の写し）、支援計画の中身、計画の変更の理由と前後、合意の意見、身体拘束の記録の中身、好きなものの名前・使い方と写真、提案、AI の入力と結果、監査ログの前後の中身。方式は AES-GCM（256ビットの鍵）。
  - 暗号化しない項目: 日付・時刻・行動・チーム・記録した人など、さがしたり並べたりするのに使う項目。「いつ・どの行動が何回」は、端末の中で暗号化されずに残る。
  - これまでの端末の中のデータは、新しい版を開いたときに一度だけ暗号化し直す（サーバーに送り直すことはない）。同期・書き出し・AI に送る前の仮名化は、これまでどおり元の形で読む。
  - 限界: 電波がなくても記録できるように、鍵はデータと同じ端末（ブラウザの保存場所）に置く。そのため、端末そのものを開けられる人やブラウザの中を直接調べられる人からは守れない。守りの中心は、これまでどおりスマホ・パソコンのロックと端末の暗号化。ブラウザのデータを消すと、ふつうは鍵とデータがいっしょに消える。鍵だけが消えてデータが残ったときは、その行の中身は読めず、サーバーにも送らない。

#### 7.4.3 認証と MFA【決定／詳細は暫定】
- 通信は TLS、保存データは暗号化。
- 個人ごとのログイン必須（共用端末でも記録者を特定するため）。
- 【決定】多要素認証（MFA）の要否は、管理者（保護者）がチームの設定画面で個別に決められる。
- 【暫定】MFA 設定の詳細:
  - チーム全体の基準を3段階から選ぶ: 「全員必須」「支援リーダー以上は必須（既定）」「任意」。
  - メンバーごとに例外を付けられる（例: 全員必須だが、スマホを持ち込めない職員 1名は免除。任意だが、学校の先生には必須）。
  - 管理者・副管理者自身の MFA は解除できない（データの所有者であり、招待と削除の権限を持つため）。MFA の端末をなくして管理者がログインできなくなった場合は、副管理者による引き継ぎ（6.9）か、運営窓口での本人確認で復旧する。
  - どのメンバーも自分の判断で MFA を有効にできる（管理者の設定は下限であって上限ではない）。
  - 基準を厳しくしたときは、対象メンバーに次回ログインで設定を促し、7日間の猶予の後に未設定なら閲覧のみに制限する。
  - MFA の方式は認証アプリのコード、SMS、端末の顔・指紋認証（パスキー）から本人が選ぶ。
  - 共用端末では、MFA を通したログインの中で「ユーザー切替 + PIN」を使う。一定時間（既定 10分）操作がなければロックする。
  - 設定の変更履歴（誰がいつ誰の要否を変えたか）を監査ログに残す。
  - 【暫定】（2026-11-07 の試作、0020）いま作ったもの:
    - 方式は認証アプリのコード（TOTP）だけ。SMS（Supabase の有料の設定が要る）とパスキーは 14.3 #13。設定と取り外しは「あなたの設定」から。MFA を設定した人は、パスワードのあとに6けたのコードを入れるまで、ほかの画面を出さない。
    - 基準（3段階）は「同意と設定」で、例外（必須・免除）はメンバーのシートで、管理者だけが変える。副管理者・支援リーダーが送った変更は、サーバーが前の値のまま残す。
    - 閲覧のみの制限はサーバーで行う（書き込みの共通の決まりと、招待コードを作るとき）。読むことと、自分からチームを抜けることはできる。写真のファイルの保存と AI の呼び出しは、まだこの制限の外。
    - 7日の猶予の起点は、0020 を流した時刻・基準を変えた時刻・その人の例外か役割が変わった時刻・参加した時刻のうち遅いもの。猶予の間は画面の上に期限を出し、過ぎたら「閲覧だけ」と出す。
    - 自分で MFA を設定した人は、基準が「任意」でも、コードを入れていないログインでは書き込めない（パスワードだけを盗まれたときに備える）。
    - 認証アプリのスマホをなくしたときは、運営が本人と確かめてから、Supabase の管理画面で設定を外す。
- アクセスログ（誰がいつ誰の記録を閲覧・編集したか）。
- 権限は行レベルでサーバ側で強制する。
- 【決定87】パスワードは 8文字以上（決定62 の「6文字以上」を変更。漏えい済みパスワードを断る確認が無料プランでは使えないため）。
- 【決定62】パスワードを忘れたとき: ログイン画面の「パスワードを忘れた」から、登録したメールに再設定のリンク（30分有効、1回限り）を送る。メールも使えなくなった人は、管理者か支援リーダーが招待し直す。管理者本人の場合は、副管理者による引き継ぎか運営窓口での本人確認で戻す（6.9）。
  - 【暫定】作り方: Supabase の再設定メールを使い、リンクの有効期限は Supabase の設定で 30分（1800秒）にする。メールのリンクを開くと「新しいパスワード」の画面だけが出て、決めるまでほかの画面には進めない。期限切れ・使用済みのリンクを開いたときは、ログイン画面でそのことを知らせる。送った画面では、そのメールが登録されているかどうかは知らせない（他人の登録の有無を探れないようにするため）。
  - 【暫定】Supabase の標準のメール送信では文面を変えられず、メールは英語になる。画面に「英語のメールが届く」と日本語で添える。日本語の文面は `supabase/email-templates/` に置き、自分の SMTP（メール送信の仕組み）をつないだら使う。標準のメール送信はプロジェクトの組織のメンバーにしか届かず、1時間に送れる数も少ないため、実際に使い始める前に SMTP をつなぐ必要がある。

#### 7.4.3a チーム間の分離と運営者のアクセス【決定45】
- 記録・グラフ・写真・睡眠・場所・支援計画・監査ログなど、対象者に関わるデータにはすべてチームの印を付ける。見られるのは、招待されて承認されたチームのデータだけ。
- 分離は画面で隠すのではなく、データベースの行レベルセキュリティで強制する。アプリにバグがあっても、他チームのデータは返さない。
- 複数の対象者を担当する職員は、チームごとに別々に招待される。アプリ内で対象者を切り替えて使う。あるチームのメンバーからは、その職員がほかに担当するチームの存在も記録も見えない。
- 公開前に、データの種類ごとに「他チームの記録を読めない・書けない・消せない」ことを自動テストで確かめる。外部の脆弱性診断（7.4.6）でも重点的に確認してもらう。
- 運営者（アプリを運営する側）はデータベースの管理画面から技術的には全データを見られるため、次のルールを置く:
  - 運営者がデータを見るのは、問い合わせ・障害への対応と、法令に基づく求めがあったときだけ。
  - 管理画面に入れる人を最小限にし、多要素認証を必須にする。入った記録を残す。
  - 運営者が見る場合とその範囲を、利用規約とプライバシーポリシーに書く。

#### 7.4.4 漏えい時の法的対応【決定（遵守すること）／期限は要確認】
- 要配慮個人情報を含む漏えい・滅失・毀損は、個人情報保護法に基づき個人情報保護委員会への報告と本人への通知の対象になる。報告の期限（速報・確報）は法令と委員会のガイドラインで確認し、運用手順に明記する。
- 報告の主体（アプリ提供者か、利用する法人か）は、データの管理責任の整理（委託か第三者提供か）によって変わるため、利用規約で定める【未決定】。

#### 7.4.5 準拠を表明する公的な指針【暫定・要確認】
導入先の種別に応じて、次の指針に沿うことを説明資料に明記する。いずれも最新版の内容を確認したうえで対応表を作る。
- 福祉事業所: 個人情報保護委員会・厚生労働省「福祉関係事業者における個人情報の適正な取扱いのためのガイダンス」
- 学校: 文部科学省「教育情報セキュリティポリシーに関するガイドライン」
- 自治体導入の場合: 政府のクラウドサービス安全性評価制度（ISMAP）登録事業者の利用を検討

#### 7.4.6 第三者による確認【暫定】

### 7.5 法令・倫理【決定（遵守すること）／対応方針は暫定】
- 障害に関する情報は個人情報保護法上の**要配慮個人情報**。取得時の本人（未成年は保護者）同意を取得・記録する。
- 外部の AI サービスへ記録を送る場合は、別途同意を取る。送信前に氏名・固有名詞を仮名化し、AI提供者側で学習に使われない契約・設定を選ぶ。
- データ保管先は国内リージョンを原則とする。
- 【決定47】AI「あり」モードでは、海外の事業者（試用では Anthropic、米国）の API に記録を送ってよい。記録の保管先は国内のまま変えず、送るのは AI を呼ぶときの仮名化した入力だけ。
- 【暫定・要確認】海外の事業者へ送るときの条件:
  - 個人情報保護法の「外国にある第三者への提供」（第28条）として扱い、AI を「あり」にするときの同意画面で、送り先の国名（米国）、その国の個人情報保護の制度（個人情報保護委員会が公表している情報を案内）、送り先が取っている保護の措置を示してから同意を取る。
  - 送り先が取っている保護の措置として示すもの: API に送ったデータを学習に使わないこと、保存期間、削除の方法。Anthropic の契約と設定は Phase 1b 着手前に確かめ、下書きに書く。
    - 【暫定】（2026-11-07 の試作）2026-11-07 に Anthropic の公開ページで確かめ、同意画面の下書きに次のことを書いた: API で送ったものを学習に使わない（契約で別に決めたときを除く）。送ったものと答えは受け取ってから30日以内に自動で消える（利用のきまりに反する疑いがあるとき・法令で求められるときは長く残ることがある）。個別に消してもらう申し込みはできず、30日以内の自動の削除が消す方法になる。米国の制度は、個人情報保護委員会の「外国制度（アメリカ合衆国）」のページへのリンクで案内する。どのページも内容は取り込まず、リンクだけを置く。
    - 【暫定】AI の同意の文面には、利用規約などの同意とは別の版（`ai-draft-2026-11-07`）を付ける。
    - 【暫定】（2026-11-08 の試作）手順の下書き（6.15）で送るもの（行動の名前・定義、ほかの望ましい行動・代替行動の名前）を同意の文面に書き足し、版を `ai-draft-2026-11-08` にした。
    - 【未決定】古い文面（ai-draft-2026-11-07 まで）で同意したチームが、手順の下書きを使う前に同意し直す必要があるか。いまは決定91 と同じく「なし」に戻さず、そのまま使える。
    - 【決定91】古い文面（draft-2026-11-05）で AI に同意したチームは、新しい文面（ai-draft-2026-11-07）で同意し直さなくても「なし」に戻さない。今回の変更は送り先の扱いの説明を書き足したもので、送るものは変わらないため（決定79 の「同意を取り直す」の例外）。
  - 同意は管理者（保護者）が取り、同意の日時と示した内容の版を記録する。同意を取り消したら、そのチームは AI「なし」に戻る。
  - 【暫定】同意の記録はサーバー（`consents` 表）にも残し、端末から同期する。書いたあとは変えられず、見えるのは同意した本人と、そのチームの管理者・副管理者だけ。
  - 【暫定】（2026-11-07 の試作、決定88）同意の取り消しは、チームの設定の「同意を取り消して『なし』に戻す」で行う。「なし」に戻すことが、そのまま取り消しになる（取り消しだけの操作は作らない）。
    - 【決定89】取り消せるのは今の管理者だけ。管理者を引き継いだあと、前に同意した人が自分の同意だけを取り消すことはできない（取り消したいときは今の管理者に頼む）。そのチームの AI の同意（同意した人がだれでも）に、取り消しの日時を付ける。この日時はサーバーが「なし」になったときに自分で書き（マイグレーション 0013）、端末から同意の行を書きかえることはできない。取り消しも監査ログに残る。
    - 「あり」に戻すには、今の管理者本人が改めて同意する。取り消した同意や、ほかの人の同意では「あり」にできない（サーバーが「なし」のまま残す）。
    - 取り消しても、端末に残っている AI の結果は消さない。ほかのメンバーには、次の同期で AI タブが出なくなるだけで、個別のお知らせはない。
    - 弱いところ: 同期は行ごとに新しいほうを残すため、管理者が2台の端末を使い、古い内容のままの端末からチームの設定を送ると、AI が「なし」に戻って同意も取り消されることがある。そのときは同意し直せば戻り、監査ログで何があったか分かる。
  - 【決定79】同意文面は本書作成者が下書きし、その下書きで試用を始める。条文の当てはめ（委託・仮名化の扱いを含む）と文面は、試用中に法律の専門家に確認する。文面が変わったら、同意を取り直す（Consent に文面の版が残る）。
- 【決定80】対象者が成人で、本人が同意の内容を理解しにくく、保護者が成年後見人でない場合も、試用は保護者の同意で始める。できる範囲で本人にも分かる言葉で説明する。これでよいかは、試用中に法律の専門家に確認する。
- 【決定56】使っている間は、古い記録を自動では消さない。消えるのは管理者がチームを削除したとき（7.6）。退所・卒業した職員はアクセスが止まるだけで、記録はチームに残る。
- 【要確認】プログラムの医療機器該当性。診断・治療目的でないことを明示する設計とするが、厚労省の該当性判断基準に照らして確認する。【決定78】確認は料金をとる前に行う（無料・5家族の試用はそのまま始める）。
- 第三者提供（学校 ↔ 施設 ↔ 家庭）は、管理者（保護者）の同意のもとで行われる設計にする。

### 7.6 データ所有とポータビリティ【暫定】
- 利用者はいつでも自分（自分の対象者）のデータを CSV で取り出せる。
- サービス終了時のデータ返却を規約に明記する。
- 【暫定】チームの削除（利用をやめるとき）は管理者だけができる。削除を申し込むと30日間は取り消せ、その後に記録・写真・場所などチームのデータをすべて消す。監査ログには「いつ・誰がチームを削除したか」だけを残し、記録の中身は残さない。削除の前に CSV で持ち出すよう案内する。
- 【決定98】メンバーが自分でできるのは「チームを抜ける」だけ（「あなたの設定」から）。抜けても、その人が付けた記録は対象者の記録としてチームに残る（記録者名は「退会したメンバー」と表示）。アカウント（メールアドレス）そのものの削除は、運営者に頼む。管理者は、管理者の引き継ぎ（6.9）をしてからでないと抜けられない。
  - 【暫定】（2026-11-07 の試作）抜ける前に、まだ送っていない記録を送る。サーバーの `leave_team`（マイグレーション 0019）が自分のメンバーの行に「削除」を付け、その時点からそのチームのデータは読めなくなる。端末に残ったそのチームのデータは、次の同期で消える。

## 9. AI設計方針【暫定】

- 【決定】AI機能は「あり / なし」をチーム設定で切り替えられる。「なし」では外部 API を一切呼ばず、記録・グラフ・共有・支援計画の全機能が完全に動作する。
- 【暫定】既定は「なし」。「あり」に切り替える際に、送信先と仮名化の内容を示して管理者の同意を取る。「なし」モードでは AI タブ・AI画面を表示しない。
- 【暫定】「あり」の場合は LLM API を利用（試用では Anthropic の Claude API）。海外事業者への送信は認める（決定47、条件は 7.5）。試用ではハッカソンのクレジットを使うため、提供者は Anthropic（米国）、モデルは Sonnet 5.5（14.2 #36）。試用後の提供者・モデルは、費用と精度を見て改めて決める。
- 【暫定】AI 呼び出しは単一のアダプタ層に閉じ込め、提供者の差し替えと「なし」モードを同じ仕組みで実現する。
- 入力は仮名化（氏名・施設名・地名を置換）し、必要最小限の期間・項目に絞る。
  - 【暫定】（2026-11-07 の試作）置きかえるのは、対象者の呼び名（→対象者）、対象者の「通っているところ」（→通っているところ）、メンバーの呼び名（→支援者A・B…）、登録した場所と記録に残る場所の名前（→場所A・B…）。分析・提案・まとめのどれでも同じ置きかえをする。「学校」のような一般的な言葉を「通っているところ」に書くと、メモの中の同じ言葉も置きかわる。ここにない固有名詞（友だちの名前など）は置きかわらない。
- 出力は JSON スキーマで構造化し、画面ではカード形式で表示。自由文のままは出さない。
- システムプロンプトに「ガイダンスの原則（非嫌悪、機能等価、先行子優先、QOL）」と「禁止事項」を記載。
- 出力後フィルタ: 禁止語（罰、弱化、拘束、隔離、取り上げ、叱る、無視を続ける 等）を検出したら破棄・再生成。【決定76】「無視（計画的無視）」は、行動分析の専門家が扱いを決めるまで AI に提案させない（禁止語に入れておく）。家族や職員が自分で計画に書くことはできる。
- 医療機器該当性の観点から、AI は「診断」「治療方針」という語を使わない。
- 【決定84】AI を呼ぶサーバー側の処理は、画面と同じ Cloudflare Pages の関数（Pages Functions、`/api/ai`）に置き、Supabase には移さない。ログインのあとは、ログインした本人の資格で Supabase に問い合わせ、チームの一員か・AI「あり」か・回数が残っているかを確かめる（service_role key は使わない）。Anthropic の API キーは Cloudflare の暗号化された環境変数に入れ、画面側のコードには置かない。Supabase の準備前でも AI を試せるようにするため。同じサイトの画面からの呼び出しだけを受け、サイト全体の1日の回数の上限を設けられる。スマホのアプリ（iOS・Android、Capacitor）の画面は端末の中から開かれるので、公開先の `/api/ai` を住所つきで呼び、サーバーはアプリの呼び出し元（`capacitor://localhost`・`https://localhost`）も受け付ける（決定133）。1人ごとの回数の上限（決定63）は、ログインができるまで端末側で数える。
- 【暫定】ログインができたので、1人ごと（決定63）とチームごと（決定60）の回数はサーバーで数える（`ai_runs` 表と `take_ai_run`、マイグレーション 0009）。アプリ全体の月の上限（14.2 #36 (2)、月80ドル）は、1回 約0.05ドルとして月1600回で数える（0011）。ボタンを押すと、AI を呼ぶ前に1回と数え、上限を超えていれば AI を呼ばない。閲覧者・チーム外の人・AI「なし」のチームは断る。端末側の数えは、画面に残り回数を出すために残す。Supabase の設定があるのにログインしていないときは AI を呼ばない（安全側に倒す）。
- 【決定99】使った金額の見張り（クレジットの残り・期限の前の知らせ）はアプリでは作らず、Anthropic の Console の利用額の上限と通知に任せる。運営者が Console で設定する。
- 【暫定】Supabase の設定がない公開（端末内だけの版。審査の人が「サンプルで試す」から試す版）では、ログインなしで AI を呼べる。そのときは、サイト全体の1日の上限（Cloudflare の KV `AI_USAGE`、回数は `AI_DAILY_LIMIT`、既定 30回）が必須で、つながっていなければ AI を呼ばない。1人ごとの回数は端末側で数える。

## 付録A 管理職向けセキュリティ説明（1ページ）

導入説明会や稟議の添付資料として、そのまま使える形にしています。詳細は 7.4〜7.6 を参照。

2026-11-07 の試作の姿に合わせて書いています。まだできていないものには「（予定）」を付けています。

**1. 何を集め、何を集めないか**
集めるのは、行動の記録（いつ・どこで・何が・何回・どのくらい）、ABC記録、支援計画、チームのやり取りです。
集めないのは、本人の実名（ニックネーム運用可）、職員や家族がいまどこにいるかの位置（記録に残るのは「施設」のような場所の名前だけ）、本人や他の人の顔写真、音声です。AI への送信は既定で「なし」で、使う場合は保護者の同意と仮名化が条件です。

**2. 誰が見られるか**
データの所有者は保護者・本人です。施設や学校の職員は、保護者の招待を受けた人だけが、指定された役割（閲覧者 / 支援者 / 支援リーダー）の範囲で見られます。退職や退所のときは保護者・副管理者・支援リーダーがその人を停止します。停止したその時点から、サーバーのそのチームのデータは読むことも書くこともできなくなり（サーバー側の仕組みで止めます）、端末に残ったデータも次の通信で消えます。ログインそのものを切ることは（予定）です。保護者に何かあったときに備えて、家族や後見人を「副管理者」に指名でき、引き継ぎの手順もアプリに用意しています。

**3. どう守るか**
一人ひとりにログインがあり、誰が何を変えたか（記録・計画・メンバー・設定）がすべて記録に残ります。誰が何を見たかを残すことは（予定）です。施設・学校の職員は、支援リーダーであっても記録を消すことも、履歴を書き換えることもできません。記録を削除できるのはデータの所有者である保護者だけで、その場合も「誰が・いつ・何件消したか」は監査ログに残り、誰にも消せません。多要素認証（スマホの認証アプリのコード）は、保護者が「全員必須」「支援リーダー以上は必須」「任意」から選び、職員ごとの例外も設定できます。必須の人が7日のうちに設定しなければ、設定するまで閲覧だけになります（サーバーで止めます）。端末をなくしたときは、本人か、チームの管理者・支援リーダーが、その端末を遠隔でログアウトさせられます。その端末からはすぐにチームのデータが読めなくなり、次につながったときに端末の中のデータを消します。新しい端末からログインがあったときは、ほかの端末の画面に知らせます。

**4. どこに保管するか**
国内のデータセンターに暗号化して保管します。第三者認証（ISO/IEC 27001、SOC 2 など）を持つ事業者を選びます。

**5. 消せるか**
保護者はいつでも自分の対象者のデータを CSV で持ち出せ、利用をやめればチームごと削除を申し込めます（申し込みから30日間は取り消せます）。いまの試作では、30日たってアプリを開いたときに端末の中のデータを消します。サーバーで使っているときは、サーバーのデータも消します（監査ログと身体拘束の記録は、扱いが決まるまで残します）。写真は強化子の削除と同時に消えます。使っている間は、古い記録を自動で消すことはありません。

**6. 漏れたらどうするか**
1人が1日に何度も記録を書き出したときは、管理者の画面に知らせます。だれがどの日にチームを開いたかも残しています。万一の漏えいは、個人情報保護法に基づいて個人情報保護委員会に報告し、本人に通知します。影響を受けた記録と、そのとき見られる立場にあった人は、監査ログとメンバーの履歴から特定できます。

**7. 何に沿うか**
福祉事業者向けの個人情報ガイダンス、学校向けの教育情報セキュリティの指針に沿って設計し、リリース前に外部の脆弱性診断を受けます。

**施設側にお願いする運用**: 退職時のアカウント停止、共用端末の離席時ロック、招待リンクを不特定多数に貼らない、月1回の監査ログ確認（チーム画面の「監査ログ」で、管理者・副管理者・支援リーダーが見られます）。
